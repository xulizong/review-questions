# `callBackDatasetFull` 面试问题与答案

本文只整理 `callBackDatasetFull` 调用链中可能被追问的问题和答案，按照执行顺序、数据集选择、知识召回、字段与维值召回、LLM与异常处理五类划分。

## 1. 整体执行顺序与并发

### 1.1 请完整说明 `callBackDatasetFull` 从 RPC 入口到 DTO 返回的执行顺序。

**答案：** RPC 层先校验 `datasetIdList`、`query` 和 `erp`，随后调用 `DatasetCallBackService.callBackDatasetFull`。领域层创建 `SimpleRecallContext`，并行完成 query 切词和候选数据集准备，然后依次执行数据集选择、知识召回；确定最终数据集且存在字段候选后，启动异步 LLM 补字段任务，主线程同时准备关键词向量，并顺序执行字段召回和值召回。

主线程召回完成后等待 LLM 补字段结果，只补入尚未召回的字段，再依次执行 LLM 字段和值精排、规则合并和结果组装。`DatasetCallBackService` 随后触发候选数据集更新，RPC 层把 BO 转成 DTO、补充总耗时并返回。

### 1.2 query 切词和候选数据集准备为什么可以并行执行？二者在什么位置汇合？

**答案：** query 切词只依赖原始 query 和 LLM，候选数据集准备只依赖 `erp`、`datasetIdList`、`bookId` 以及数据集服务，二者没有前后依赖，并且分别写入 `SplitWordContext` 和 `BaseDatasetInfo`，所以可以并行。

`runSplitAndCandidatePrepare` 通过两个 `CompletableFuture.runAsync` 启动任务，并在 `CompletableFuture.allOf(...).join()` 处等待两边完成。它们的结果在 `DatasetRecallStage` 汇合，因为选表既需要切词得到的 `dataSource/query`，也需要已经加载好的候选数据集。

### 1.3 query 切词内部为什么并行调用两次 LLM？两次结果如何合并？

**答案：** 两次独立调用可以降低单次 LLM 漏词或调用失败带来的影响；任意一次异常都会被 `safeSimpleSplit` 转为空结果，不会立即中断流程。合并时，普通关键词和时间关键词分别取并集，`dataSource` 使用第一次非空结果对象中的值；第一次结果对象为空时才使用第二次。

合并后，时间词会先从普通关键词中移除。只有两次切词合并结果本身为 `null` 时，`SplitQueryStage` 才会把完整原始 query 作为兜底关键词；如果合并时原本存在关键词，但移除时间词后变为空，当前代码不会再次触发兜底。若存在 `dataSource`，还会把它加入普通关键词集合。

### 1.4 哪些阶段严格按顺序执行，哪些阶段存在并发或交叠执行？

**答案：** 数据集选择、知识召回、结果汇合、LLM 精排和规则合并严格按顺序执行；字段召回与维值召回在当前编排中也是先字段、后维值，并没有并行。并发主要有三处：query 切词与候选数据准备并行、切词内部两次 LLM 并行、已召回知识的解释文本按知识并发切分。

知识召回结束后，LLM 补字段任务会与主线程的关键词向量准备、字段召回和值召回交叠执行。主线程完成值召回后才等待 LLM 结果，两条支线汇合后继续精排和规则合并。

### 1.5 哪些条件会导致流程提前返回？提前返回时响应中还会保留哪些内容？

**答案：** 如果候选数据集详情为空，或者选表阶段没有得到最终数据集，`executeFull` 会提前结束；`makeFinalCall` 仍会返回已经记录的阶段统计，但不会包含最终数据集、字段和知识。入参校验失败或未降级的异常不属于成功提前返回，而是由 RPC 层返回错误响应。

如果已经选出最终数据集，但该数据集没有可用字段候选，流程会在知识召回后提前结束。此时响应仍保留最终数据集信息和已经召回的知识，但字段列表为空，不再执行字段召回、维值召回和后续合并。

### 1.6 `SimpleRecallContext` 在整个流程中保存了哪些核心状态？为什么各 Stage 通过共享上下文传递结果？

**答案：** 它保存原始入参、token 上报上下文、阶段耗时、候选数据集及字段缓存、切词结果、最终数据集、知识及知识切词、字段和值的关键词与向量、字段和值召回结果，以及最终合并字段。各 Stage 读取前置结果并写入自己的子上下文，避免在每层方法之间传递大量复合参数。

显式保存 token 和业务状态也能让异步任务在线程切换后继续读取所需信息。LLM 补字段支线会创建独立 context，但复用已经准备好的数据集字段信息和知识结果，避免直接并发修改主 context 的字段结果。

### 1.7 单候选数据集场景为什么不需要执行数据集向量召回和 LLM 选表？

**答案：** `loadCandidates` 发现只有一张候选表时，会直接把它设置为最终数据集，因此不存在表间歧义，也无需再通过向量或 LLM 比较。当前代码仍会执行一次字符串匹配，但随后检测到最终数据集已经存在，立即绑定字段并返回，不再进入向量召回和 LLM 选表。

### 1.8 各阶段执行耗时如何记录？异常发生时是否还能留下阶段统计？

**答案：** 各 Stage 通过 `StageExecutionSupport.runStep` 统一计时，并在 `finally` 中写入阶段名称、执行耗时和可选的 LLM 耗时；`addExecutorStats` 使用同步方法，支持并发阶段共同写入。即使阶段动作抛出异常，这条统计仍会写入 context。

如果异常在阶段内部被捕获并降级，统计会随正常响应返回；如果异常继续向 RPC 层抛出，context 内虽然已经留下统计，但接口最终返回错误响应，不会把这份阶段统计转换到 DTO 中。

## 2. 数据集选择与作用域

### 2.1 `datasetIdList` 表示多表聚合，还是从多张候选表中选择一张最终数据集？

**答案：** 在 `callBackDatasetFull` 中，`datasetIdList` 表示候选数据集范围，不表示多表聚合。系统会从候选表中确定零张或一张最终数据集，后续知识、字段和值召回都只围绕这张表执行，最终结果中的数据集列表正常也只有一项。

### 2.2 数据集字符串匹配按照什么顺序判断 `dataSource`、表名和原始 query？

**答案：** 匹配顺序是：先判断 `dataSource` 与表名是否完全相等；没有命中时，再判断候选表名是否出现在原始 query 中；仍未命中时，最后判断 `dataSource` 与表名是否互相包含。每层一旦出现命中就停止继续尝试下一层。

这里的匹配表名优先使用数据集 `datasetCaption`，为空时才使用 `schemaName`；原始 query 中的表名匹配使用大小写不敏感的文本查找。

### 2.3 字符串匹配出现唯一命中、多个命中和没有命中时分别如何处理？

**答案：** 唯一命中时直接设置最终数据集，并跳过数据集向量召回和 LLM 选表。多个命中时只把候选集收窄为命中的数据集，不直接决定最终表，继续交给向量召回；没有命中时保留原候选集，同样继续执行向量召回。

### 2.4 数据集向量召回比较了表名、描述和摘要中的哪些向量？`dataSource` 有什么作用？

**答案：** `callDatasetVector` 同时查询数据集空间中的表名向量、描述向量和摘要向量，并通过加权排序合成最终分数。描述和摘要始终使用完整 query 的向量；表名在存在 `dataSource` 时使用 `dataSource` 的向量，否则也使用完整 query 的向量。

因此，`dataSource` 是切词阶段提取的专用表名信号，用来减少完整问题中指标、时间和筛选条件对表名相似度的干扰。查询同时用候选 `datasetId` 做 OR 过滤，不会搜索候选范围以外的数据集。

### 2.5 什么情况下可以直接使用向量 top1，什么情况下还要交给 LLM 选表？

**答案：** 向量只返回一个候选且分数达到 `vectorFinalMinScore` 时，可以直接选择该表。存在多个候选时，只有 top1 达到最低分，并且它相对 top2 的分差比例达到 `vectorFinalDiffRatio`，才直接选择 top1。

其余情况下，系统把向量结果裁剪到 `llmTableCandidateLimit` 后交给 LLM 选表。即使只有一个向量候选，只要分数没有达到直接确认阈值，也仍会进入 LLM 选择。

### 2.6 LLM 返回空对象、非法 `tableId` 和直接调用失败时，系统分别如何处理？

**答案：** LLM 返回空对象、`tableId` 为空，或者返回的 `tableId` 不在当前候选集中时，系统都会回退到向量排序第一的数据集。该回退只要求候选集非空，代码没有再次校验 top1 分数。

如果 `selectFinalTable` 调用本身在重试后仍抛出异常，`llmSelect` 没有捕获并执行 top1 回退，异常会继续向上抛出，最终由 RPC 层返回错误响应。

### 2.7 为什么必须先确定最终数据集，再执行知识、字段和维值召回？

**答案：** 不同数据集可能存在同名字段、相同业务词但不同解释，以及相同展示值对应不同列。先确定最终数据集，才能绑定该表的有效字段缓存，并把知识、字段和值检索限制在同一张表中，避免其他候选表的知识或字段混入结果。

### 2.8 `datasetId` 与 `bookId + datasetId` 分别限定了哪些数据和配置范围？

**答案：** `datasetId` 主要限定实际数据集范围，包括最终表的 schema、原始字段向量、基础维值向量以及内存中的字段候选。字段和值召回即使查询 Vearch，也只能接受最终 `datasetId` 下的结果。

`bookId + datasetId` 限定该 book 对这张数据集配置的语义信息，包括字段启停、别名、同义词、业务知识、自定义维值和知识召回配置。这样同一数据集在不同 book 下可以拥有不同的业务解释和召回行为。

### 2.9 字段启停、别名和同义词在候选数据集准备阶段如何影响后续召回范围？

**答案：** 候选准备阶段先读取数据集原始 schema，再合并 book 下的字段语义配置。存在字段配置时，明确设置为停用的字段会从候选字段中删除，之后不会进入选表字段提示、字段召回和最终结果；没有字段配置时，原 schema 字段默认全部参与。

别名和同义词会绑定到对应 `columnId`，成为字符串匹配、别名或同义词向量召回以及 LLM 选表可见的名称。若开启 `aliasBlockOriginRecallEnabled`，配置了别名的字段会屏蔽原名召回，要求通过别名或同义词命中。

### 2.10 当前方法为什么不能直接支持跨多张表的联合查询或聚合？

**答案：** 当前上下文只有一个 `finalCallDataSet`，选表流程会把多张候选表收敛成一张，后续知识、字段和值召回也都只接收这个最终 `datasetId`。最终组装同样只创建一个数据集结果，没有保存多表关系、关联条件或跨表字段归属，因此不能直接表达 JOIN 或跨表聚合。

## 3. 知识召回机制

### 3.1 知识配置的源数据在哪里？Vearch 在知识召回中承担什么职责？

**答案：** 知识配置通过 `semanticService.getSemanticKnowledge(bookId, datasetId)` 从语义配置服务加载，包括知识词条、解释、召回策略、关键词以及两个扩展开关。语义配置服务是当前知识的有效数据来源。具体调用的是c-side的方法，存储在了MYSQL里面。

Vearch 保存知识的向量索引，负责在文字没有直接命中时进行语义相似度检索。它返回的是 `KnowledgeEmbDocument` 候选及相似度分数，不是知识配置的唯一来源。

### 3.2 为什么知识召回使用最终 `bookId + datasetId` 作为范围，而不能在全部候选数据集中搜索？

**答案：** 同一个业务词在不同数据集中的解释可能不同，因此必须先选定最终数据集，再加载和检索该数据集的知识。`KnowledgeRecallStage` 传入最终数据集的 `tableId`，Vearch 查询也使用 `bookId AND datasetId` 过滤。

当前代码只支持 `bookId + datasetId` 粒度，单独按 `bookId` 加载知识的代码尚未开放。

### 3.3 跟随整体召回、自定义召回和所有请求都召回三种策略有什么区别？

**答案：** `FOLLOW` 主要依赖向量相似度召回；`CUSTOM` 在原始 query 包含配置关键词时直接召回，不受向量阈值和条数限制，未命中时当前实现仍可继续参与向量召回；`ALL_TIME` 只要选中当前数据集就直接召回。

此外，无论配置哪种策略，只要原始 query 直接包含知识词条，代码都会将其作为 `CONTAINS` 方式直接召回。

### 3.4 原始 query 直接包含知识词条时，为什么不需要依赖向量相似度？

**答案：** 代码直接执行 `baseQuery.contains(knowledgeBO.getWord())`。只要原始问题包含完整知识词条，就能确定用户明确提到了该概念，因此直接标记为已召回，不需要承担向量阈值造成的漏召回风险。

### 3.5 为什么要从知识向量查询结果中排除已经通过规则命中的知识？

**答案：** 规则命中的知识已经确定需要使用，不应再次作为向量结果重复加入，也不应占用向量召回的最终条数。`excludeKnowledgeIds` 会在 Vearch 返回后过滤这些知识，并在统一重排时再次校验。

这里的排除目前是 Java 侧结果过滤，并没有作为 `knowledgeId` 排除条件直接传入 Vearch。

### 3.6 正常情况下规则已经命中知识后，当前请求是否仍可能访问 Vearch？为什么？

**答案：** 会。只要 query 切出的普通关键词或时间关键词不为空，`knowledgeCall()` 在完成规则匹配后仍会调用 `searchKnowledge()`，继续寻找当前数据集下其他可能相关的知识。

已经通过规则命中的知识会被排除，因此这次向量查询主要用于补充尚未命中的知识；只有待向量化关键词为空时才会跳过。

### 3.7 `useColumnCall` 和 `useValCall` 分别控制什么？它们是否是字段召回和值召回的总开关？

**答案：** `useColumnCall` 控制知识解释拆出的关键词是否加入字段召回，`useValCall` 控制这些关键词是否加入维值召回。它们只控制知识扩展方向，不是两条召回链路的总开关。

即使两个开关都关闭，知识仍会出现在本次召回结果中，只是不拆分解释参与后续召回；原始 query 切出的关键词仍会正常参与字段和值召回。

### 3.8 知识解释拆出的关键词如何进入字段召回或维值召回？

**答案：** `KnowledgeRecallStage` 只选择本次已召回且至少开启一个扩展开关的知识，调用 `SimpleKnowledgeSplit.splitBatch()` 拆分知识解释。拆分结果以 `knowledgeId` 保存。

后续 `initRecallKeywords()` 根据开关分流：`useColumnCall=true` 时加入字段关键词集合，`useValCall=true` 时加入维值关键词集合，两个开关都开启时同时进入两边。

### 3.9 “山河四省表示山东、山西、河南、河北”应如何配置召回策略和关键词扩展方向？

**答案：** 这条知识只在用户提到特定区域概念时有用，更适合配置自定义召回，并补充“鲁晋豫冀”“四省区域”等触发关键词。用户直接说“山河四省”时，也会因为 query 包含知识词条而直接命中。

解释中的“山东、山西、河南、河北”属于字段具体值，因此适合配置 `useValCall=true`、`useColumnCall=false`，用于召回省份字段中的这些维值。

### 3.10 所有请求都召回为什么能避免漏召回，同时也可能引入无关字段或维值候选？

**答案：** `ALL_TIME` 不检查 query 是否相关，只要选中当前数据集就召回，因此不会因为关键词或相似度不足而遗漏知识。但它也意味着无关问题会携带这条知识。

如果该知识还开启了 `useColumnCall` 或 `useValCall`，解释中的词会进入字段或维值召回，可能产生与当前问题无关的候选。

### 3.11 Vearch 召回出的知识为什么还要与语义配置服务加载的全量知识进行校验？

**答案：** Vearch 中可能残留已经从配置侧删除的旧索引。`rerankVectorKnowledge()` 会检查 Vearch 返回的 `knowledgeId` 是否仍存在于语义配置服务加载的 `fullKnowledgeIdSet` 中，不存在就按脏数据过滤。

这保证最终返回的知识以当前有效配置为准，而不是直接信任向量索引中的历史数据。

### 3.12 动态知识接口失败时为什么不会中断完整召回流程？

**答案：** 动态知识接口只负责为已经召回的自定义动态知识更新解释文本，不负责决定知识是否命中。调用失败时，`processDynamicKnowledge()` 捕获异常并记录日志，原有知识解释仍可继续使用。

因此动态内容属于可降级的补充信息，不应该因为更新失败而让整次数据集召回失败。

## 4. 字段召回与维值召回

### 4.1 字段召回和值召回的目标分别是什么？最终结果如何通过 `columnId` 关联？

**答案：** 字段召回解决“用户说的词对应数据集中的哪一列”，例如将“销售额”匹配到 `columnId=102` 的“成交金额”；维值召回解决“用户说的具体值属于哪一列，以及底表实际使用什么值”，例如将“华东”匹配到 `columnId=101` 的“地区”字段，并得到真实编码 `EAST`。

字段结果保存在以 `columnId` 为键的 `callColumnResult` 中，维值结果保存在同样以 `columnId` 为键的 `callValueResult` 中。后续按相同的 `columnId` 合并，就能把字段及其维值关联起来。

### 4.2 为什么字段召回先做字符串、别名和同义词匹配，剩余关键词才执行向量召回？

**答案：** 字符串匹配是确定性匹配，精度更高且不需要调用 Vearch。`ColumnRecallStage` 会使用当前 active 字段的原名、别名和同义词，判断名称和关键词或原始 query 的文本关系，命中结果直接记为 `1.0` 分。

命中的关键词会从字段侧剩余关键词中删除，只有未命中的词才进入向量召回。这样既减少向量查询量，也避免本来可以确定命中的字段被语义相近但不准确的字段干扰。

### 4.3 字符串没有直接匹配时，为什么在同一个数据集的 Vearch 字段空间中仍可能找到正确字段？

**答案：** 字符串匹配失败只表示用户用词和字段名称在文字上不相同，不代表数据集中没有语义对应的字段。例如用户说“销售额”，数据集字段实际叫“实付金额”，两者无法通过字符关系命中，但向量可能判断它们语义接近。

Vearch仍然只查询当前 `datasetId` 下已经存在的字段，只是把比较方式从文字匹配改成向量相似。若数据集中确实没有相关字段，Vearch也不能创造字段，只能返回达到相似度阈值的现有候选。

### 4.4 `VearchDocGatewayImpl.searchDoc()` 的请求包含哪些核心字段？返回结果使用哪个实体承接？

**答案：** 请求使用 `SearchQueryRequestParam`，核心字段包括 `db_name`、`space_name`、`vectors`、`filters` 和 `limit`。其中 `vectors` 包含向量字段名、关键词 embedding 和 `min_score`，`filters` 用于限定 `datasetId` 等结构化范围。

`searchDoc()` 的返回外层由泛型响应 `SearchQueryResponseResponseDO<T>` 承接。原字段查询传入 `DatasetSchemaEmbDocument.class`，因此具体文档被反序列化成 `DatasetSchemaEmbDocument`，代码读取 `documents.get(0)`。

### 4.5 字段原名向量召回为什么使用 `DatasetSchemaEmbDocument`，字段别名和同义词为什么使用 `SchemaSynonymsEmbDocument`？

**答案：** 原字段空间存储的是数据集字段本身，因此使用 `DatasetSchemaEmbDocument`，其中包含 `datasetId`、`columnId`、中英文名称、字段描述、字段类型和字段名称向量。查询时比较的是 `vectorColumnCn`。

别名和同义词属于 book 下的业务配置，存储在独立空间中，所以使用 `SchemaSynonymsEmbDocument`，其中包含 `bookId`、`datasetId`、`columnId`、词条类型、词条内容和 `vectorSynonym`。召回后系统会将它转换成统一的字段召回结果结构。

### 4.6 `SCALAR`过滤与 `FLAT + InnerProduct` 向量检索在一次字段查询中如何配合？

**答案：** `SCALAR` 用于 `datasetId` 这类普通字段的精确过滤，逻辑上先把候选范围限定在当前数据集；别名和同义词查询还会同时限定 `bookId`。它不负责理解用户 query 的语义。

范围确定后，`FLAT` 会对候选向量逐个比较，`InnerProduct` 使用内积计算分数。当入库向量和查询向量都归一化时，内积等价于余弦相似度，分数越高表示语义越接近。

### 4.7 `datasetId`过滤、`min_score`、Vearch查询窗口和Java侧 topN 分别解决什么问题？

**答案：** `datasetId` 保证不会召回其他数据集的字段，`min_score` 过滤语义相关性过低的结果，Vearch查询窗口控制一次最多取回多少条初始候选。原字段查询窗口由 `vectorColumnSearchLimit` 控制，配置缺失或非正数时兜底为100。

Java侧 topN 是初召后的二次收敛，每个关键词的原字段结果由 `vectorColumnTop` 控制，默认最多保留3条。别名和同义词使用独立的 `vectorColumnCustomSearchLimit` 和 top 配置；Vearch窗口决定“最多取回多少”，Java侧 topN 决定“最终保留多少”。

### 4.8 基础维值、自定义维值和维度中心三种值来源有什么区别？

**答案：** 基础维值是数据集自身维度字段已有的值或编码，存放在 Vearch 基础维值空间；自定义维值是 book 和数据集下人工配置的原值、别名或同义词，存放在 Vearch 自定义维值空间。两者都使用关键词 embedding 做向量查询。

维度中心是外部维度服务，不查询 Vearch。字段通过 `dimCode` 或 `customSql` 绑定维度后，系统调用 `dimensionService.searchDimension()`，将用户词转换成标准展示值和底表编码。

### 4.9 基础维值召回和自定义维值召回分别使用什么Vearch实体？过滤条件有什么差异？

**答案：** 基础维值召回使用 `SchemaDimensionValueEmbDocument`，查询 `vectorDimCode` 和 `vectorDimValue`，Vearch侧按 `datasetId` 过滤。允许参与基础召回的 `columnId` 没有直接写入 Vearch过滤条件，而是在结果返回后通过 `baseDimColumnIds` 再过滤。

自定义维值召回使用 `SchemaCustomDimensionValueEmbDocument`，查询 `vectorDimValue`，过滤条件是 `bookId AND datasetId`。返回结果随后会转换成统一的 `SchemaDimensionValueEmbDocument` 结构，方便与基础维值和维度中心结果合并。

### 4.10 为什么维值召回不需要先确定某个字段，而可以在当前数据集的维度列中搜索后再反向关联字段？

**答案：** `ValueRecallStage` 并非完全不限定字段，它会先筛出当前数据集中非虚拟的维度字段，但不要求提前确定唯一字段。这样用户只说“山东”而没有说“省份”时，系统仍然可以在当前数据集的维度值范围内搜索。

Vearch中的每条维值文档都保存了 `datasetId` 和 `columnId`，所以命中“山东”后可以通过返回的 `columnId` 反向确定它属于哪个字段。维度中心结果也会根据维度编码找到绑定字段，并补充对应的 `columnId`。

### 4.11 如果Vearch返回的维值属于已停用字段，系统如何处理？

**答案：** 基础维值、自定义维值和维度中心结果合并后，系统会使用最终数据集的 active 字段缓存再次校验 `columnId`。如果该字段已经停用、被删除或不属于最终数据集，这条维值不会进入 `callValueResult`。

被过滤的记录会写入 `CallExecutionStats.suppressedValueRecalls`，并记录 `datasetId`、`columnId`、查询关键词、命中值、来源以及 `COLUMN_INACTIVE` 原因，用于内部排查。

### 4.12 如何设计“用户确认别名后同步到Vearch”的召回飞轮？为什么不能直接把完整 query 写成字段别名？

**答案：** 当前 `callBackDatasetFull` 没有实现自动学习飞轮。合理流程是用户确认“GMV对应成交金额”后，先把 `GMV → bookId + datasetId + columnId` 保存为业务别名或同义词配置，再生成 `GMV` 的向量，并以包含 `bookId`、`datasetId`、`columnId`、`type`、`synonym` 和 `vectorSynonym` 的 `SchemaSynonymsEmbDocument` 同步到 Vearch。

不能把“查询上个月华东地区的GMV”整句直接写成别名，因为其中混合了时间、区域、指标和查询动作，也没有唯一指向某个字段。正确做法是先提取“GMV”，再通过用户确认建立它与具体 `columnId` 的可靠映射。

## 5. LLM、结果合并与异常处理

### 5.1 已经完成规则和向量召回后，为什么还需要 LLM 补充选字段？

**答案：** 规则和向量召回以拆分后的关键词为中心，可能因切词遗漏、名称差异或阈值过滤漏掉字段。`ChooseColumnLLMStage` 直接查看原始 query、最终数据集的完整字段列表和知识文本，从整体语义上补充可能缺失的字段。

这个阶段不是替换主召回结果；主线程召回结束后，系统只按 `columnId` 把 LLM 选中但主链路没有命中的字段补入。

### 5.2 LLM补字段阶段和字段、维值精排阶段分别解决什么问题？

**答案：** LLM补字段面向最终数据集的完整 schema，目标是“补漏”；字段、维值精排面向规则和向量已经召回的候选，目标是根据 query 和知识“降噪”。

二者输入范围不同：前者可以从完整字段列表中发现新字段，后者原则上只应在现有字段和值候选中筛选。

### 5.3 LLM补字段任务为什么可以与主线程的字段、维值召回交叠执行？最终如何合并？

**答案：** 最终数据集、字段候选、原始 query 和知识已经准备完成后，LLM补字段不依赖主召回的中间结果，因此可以使用独立的 `CompletableFuture` 和单独构建的 context 执行。主线程同时进行关键词组装、embedding、字段召回和值召回。

主线程完成后通过 `future.join()` 等待 LLM，随后 `supplementMissingCallColumnResult()` 按 `columnId` 合并，只补入主召回缺失的字段。

### 5.4 当前精排逻辑为什么能够删除维值，却难以真正删除原有字段候选？

**答案：** LLM返回后，代码确实先生成了过滤后的字段集合，但随后 `mergeCallColumnResult()` 又把过滤前字段与过滤后字段取并集，因此原字段仍被保留。维值侧则直接用过滤后的 `dimValueMapRes` 覆盖原结果，所以未被 LLM 允许的值会被删除。

这意味着当前精排对字段主要不能起到删除作用，对维值才有实际缩减能力。

### 5.5 最终合并阶段如何处理 `COLUMN_ONLY`、`VALUE_ONLY`、`COLUMN_AND_VALUE` 和 `DROP`？

**答案：** `COLUMN_ONLY` 只保留字段命中；`VALUE_ONLY` 保留值命中并自动带出该值所属字段；`COLUMN_AND_VALUE` 同时保留字段和值；`DROP` 表示两侧都没有有效命中或属于召回计划外结果，直接丢弃。

这些判断以关键词为单位完成，再由 `FinalColumnAccumulator` 汇总为最终字段结构。

### 5.6 只有值命中、没有字段命中时，为什么仍然需要把该值所属字段加入结果？

**答案：** 一个维值必须依附于具体字段才能形成可执行过滤条件。例如“华东地区”命中了 `columnId=101` 下的值 `EAST`，如果不同时返回“地区”字段，后续无法知道应在哪一列使用该值。

因此 `VALUE_ONLY` 会先创建或找到值所属字段，再把展示值、真实值、类型和分数写入该字段的 `fieldEnum`。

### 5.7 日期字段、`alwaysRecall`虚拟字段和FULL表分区字段在最终收口时如何处理？

**答案：** FULL表的分区字段会从最终字段中排除；日期类型字段即使没有被 query 命中也会自动补入。Standard或 `METRIC_DATASET` 数据集里配置为 `alwaysRecall` 的虚拟字段也会自动补入。

这些都是 `RecallMergeStage` 在语义召回完成后执行的确定性收口规则。

### 5.8 query切词两次都失败、向量查询失败、LLM选表失败和LLM精排失败时分别如何处理？

**答案：** 两次切词合并结果为 `null` 时，使用完整原始 query 作为兜底关键词；如果关键词只是在后续移除时间词时变为空，则不会再次兜底。数据集、字段和知识的Vearch查询发生接口异常时会向上抛出并终止请求；基础维值和自定义维值的单关键词 `BaseException` 会被捕获后继续，维度中心异常也会被捕获。

LLM选表返回空对象或非法 `tableId` 时回退向量 top1，调用本身重试后仍失败则终止请求；LLM精排失败或返回空结果时跳过精排，保留原字段和值候选继续合并。

### 5.9 为什么部分外部调用失败可以降级继续执行，而Vearch主召回异常可能终止整个请求？

**答案：** 动态知识、维度中心单次查询和LLM精排属于补充或降噪能力，失败后仍可使用已有知识、字段和值候选。字段或知识的核心Vearch召回是主要候选来源，接口异常时系统无法判断结果是“确实没有匹配”还是“检索服务不可用”，继续返回可能产生不可信结果。

具体是否降级由各调用点是否捕获异常决定，并不是所有Vearch调用都采用完全相同的策略。

### 5.10 最终返回结果包含哪些数据？为什么不包含实际数据行和生成后的SQL？

**答案：** 返回内容包括最终数据集元数据、字段、字段下的 `fieldEnum` 维值、本次真正召回的知识以及执行统计。它不包含数据行和SQL，因为 `callBackDatasetFull` 的职责是为后续查询提供可用的表、字段、值和知识上下文，本身不负责生成或执行SQL。

### 5.11 `knowledges` 为什么只返回本次真正召回的知识，而不是数据集下加载的全部知识？

**答案：** `fullKnowledgeCache` 是当前数据集的全量知识参考集合，`recalledKnowledgeIds` 才表示经过始终召回、关键词、词条包含或向量规则命中的知识。`makeFinalCall()` 只按照 `recalledKnowledgeIds` 从全量缓存取值，避免把与本次 query 无关的知识返回给调用方。

### 5.12 后置数据集更新发生异常时，为什么不应影响已经完成的召回响应？

**答案：** 后置更新用于刷新原始 `datasetIdList` 中各候选数据集的向量元数据，不参与本次已经完成的选表、字段和值结果计算。`triggerDataSetUpdate()` 对每个数据集的异常单独捕获并记录日志，因此单个更新失败不会向上抛出并破坏召回响应。

需要注意，当前通过 `this.triggerDataSetUpdate(...)` 调用同类中的 `@Async` 方法，通常不会经过 Spring 异步代理，因此不能仅凭注解确认它一定异步执行；如果实际同步执行，更新失败仍不会改变召回结果，但可能增加接口返回耗时。

# `callBackKnowledge` 方法解读

本节整理 `callBackKnowledge` 这个"仅知识召回"接口的作用、返回内容，以及它和 `callBackDatasetFull` 的区别。核心一句话：`callBackKnowledge` 是把完整召回链路里的"知识召回"那一段单独暴露成的轻量接口，只切词、只在一个指定数据集上召回业务知识，不做选表、不做字段召回、不做维值召回、不做 LLM 精排。

## 6.1 方法作用与执行路径

### 6.1.1 `callBackKnowledge` 具体做什么？内部执行到哪几步？

**答案：** 它只跑三步（`SimpleCallDataSetExecutor.executeKnowledgeOnly`）：先 `splitQueryStage` 对 query 切词；再 `bindKnowledgeRecallDataset` 把入参 `datasetIdList` 的第一个数据集直接绑定为召回目标（不做选表）；最后 `knowledgeRecallStage` 在这个数据集上召回业务知识。`makeFinalCall` 组装结果后，最外层 `DatasetCallBackService.callBackKnowledge` 只把 `res.getKnowledges()` 这一段捞出来返回，其余（字段、维值）全部丢弃，命中为空时返回空列表。

对比 `callBackDatasetFull` 的 `executeFull`：完整版在切词、候选准备之后还要跑数据集选表、字段召回、值召回、LLM 补字段、精排、规则合并一整串，而知识版把这些全砍掉了。

### 6.1.2 为什么只取 `datasetIdList` 的第一个数据集？数据集很多怎么办？

**答案：** 知识召回的最小作用单位就是"一个数据集"——`knowledgeCallService.knowledgeCall(bookId, tableId, ...)` 只接收单个 `tableId`，知识是挂在"知识库 bookId + 具体数据集"作用域下的，脱离具体数据集就无从召回。在完整链路里，"多数据集→定一个"是由前置的选表阶段解决的，选出唯一 `finalCallDataSet` 后知识召回才在其上运行；而 `callBackKnowledge` 有意省掉选表，所以只能约定"调用方已把目标数据集确定好并放在第一个"。

这是一个信任调用方的简化约定，`datasetIdList.get(0)` 会静默忽略其余数据集。如果场景确实需要跨多个数据集召回知识，应当自己按数据集逐个调用再合并，或改走 `callBackDatasetFull` 让它先选表。

## 6.2 返回内容

### 6.2.1 `callBackKnowledge` 返回什么？每个字段是什么含义？

**答案：** 返回 `List<KnowledgeWord>`，即"本次 query 命中的业务知识词条列表"。每个 `KnowledgeWord` 有五个字段：`knowledgeId`（知识条目 ID）、`word`（词条本身，用户在知识库配置的词）、`relation`（关联关系，如"表示"）、`explanation`（知识内容/解释）、`synonyms`（该词的同义词列表）。它不含字段、维值、score，也不含数据行和 SQL。

组装逻辑在 `makeFinalCall` 里：拿召回到的 `recalledKnowledgeIds` 去 `fullKnowledgeCache` 取出每条知识完整信息，逐条映射成 `KnowledgeWord`。

### 6.2.2 举个具体例子说明返回内容。

**答案：** 设数据集配了一条知识：`knowledgeId=1001，word="GMV"，relation="表示"，explanation="商品成交总额（下单口径，未剔除退款）"，synonyms=["成交额","销售额"]`。用户问「上个月 GMV 是多少」，`callBackKnowledge` 命中这条知识，返回：

```json
[
  {
    "knowledgeId": 1001,
    "word": "GMV",
    "relation": "表示",
    "explanation": "商品成交总额（下单口径，未剔除退款）",
    "synonyms": ["成交额", "销售额"]
  }
]
```

上游拿到它，可以把 `word + relation + explanation` 拼成一句解释性上下文喂给生成 SQL 的大模型（让它对齐"GMV 是不含退款的口径"），或直接展示给用户做术语提示。它的用途是"给模型/用户补语义"，和字段是平行的、不带 columnId。

## 6.3 与 `callBackDatasetFull` 的区别

### 6.3.1 两者最核心的区别是什么？

**答案：** `callBackDatasetFull` 是完整召回引擎，产出"表 + 字段 + 维值 + 知识 + 执行统计"一整套供下游生成 SQL；`callBackKnowledge` 是它内部知识召回子阶段的独立出口，只产出"知识词条列表"一份。两者共用同一个执行器 `SimpleCallDataSetExecutor` 和同一套 `SimpleRecallContext`，是同一条流水线上按需裁剪出的不同档位。

| 维度 | `callBackDatasetFull` | `callBackKnowledge` |
| --- | --- | --- |
| 选表 | 做（`datasetRecallStage` 从多候选选一个） | 不做（直接取 `datasetIdList.get(0)`） |
| 字段召回 / 值召回 | 做（正则 + 向量 + 维度中心等多路） | 不做 |
| LLM 补字段 / 精排 | 做 | 不做 |
| 知识召回 | 做（且知识还兼任内部关键词扩充） | 做（仅此一步） |
| 返回类型 | `CallBackDatasetFullFinalDTO`（表/字段/维值/知识/统计） | `List<KnowledgeWord>`（仅知识） |
| 典型用途 | 端到端问数前的完整上下文召回 | 只想拿"命中了哪些业务知识"，做理解补充/术语提示 |

### 6.3.2 知识在 `callBackDatasetFull` 里扮演了几个角色？这和 `callBackKnowledge` 有什么关系？

**答案：** 在 `callBackDatasetFull` 里知识扮演两个独立角色。角色一是"最终产物"：召回到的知识词条被组装进返回体的 `knowledges` 返回给上游。角色二是"内部关键词扩充器"：知识召回后会对命中的知识切词（`splitRecalledKnowledge`），切出的词补充进后面的字段召回和值召回，帮忙多捞相关字段。

`callBackKnowledge` 因为不做字段召回，所以角色二根本不发生，它只保留角色一——纯粹把召回到的知识返回。这也说明"知识内容本身是保留返回的"，被丢弃的只是角色二里的一层关联关系（见下题）。

### 6.3.3 之前说知识"用完即弃"，那 `callBackKnowledge` 又确实返回了知识，怎么理解？

**答案：** "用完即弃"指的不是知识内容，而是"知识与字段之间的关联血缘"。知识内容本身在两个接口里都是保留并返回的；被丢弃的是"这条知识切出的词命中了哪个字段"这条连线——知识对象上没有 columnId，最终结果里知识和字段是两份平行清单，看不出某个字段是被哪条知识带出来的。

举例说明血缘丢失：数据集有字段成交金额（columnId=501）。用户问「上个月 GMV 是多少」，走 `callBackDatasetFull` 时，知识 1001 切出"成交额"，字段召回用"成交额"匹配到了 501。最终返回体里会同时出现知识 1001 和字段 501 两份平行清单，但字段 501 上没有任何标记说明"我是被知识 1001 带出来的"，知识 1001 也不记录"我命中了 501"。这条"GMV 知识 → 成交额 → 字段 501"的链路在结果里查不到了。

这样设计是因为下游生成 SQL 只需要"有哪些字段"和"有哪些知识"两份清单即可，谁带出谁对拼 SQL 无影响。代价是无法做召回归因/可解释性分析，这是设计上的一个已知局限。而 `callBackKnowledge` 只返回知识、不返回字段，自然也就不涉及这条血缘。
