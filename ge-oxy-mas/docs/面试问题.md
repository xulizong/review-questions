# 面试问题
## 1、对于prompt的内容，哪种形式更好呢？

对于 DataAgent，我认为好的 Prompt 主要有以下几点。

第一，任务边界要明确。需要说明当前 Prompt 负责的是意图识别、Schema 选择、SQL 生成还是结果分析，并明确禁止事项，避免一个 Prompt
承担过多职责。

第二，输入信息要完整且结构化。除了用户问题，还应提供表和字段描述、字段类型、样例值、主外键关系、数据库方言、指标口径和业务知识，并用固定标签区分不同内容。

第三，业务语义和数据口径要清晰。模型应优先使用已提供的指标定义和语义模型，不能根据字段名自行猜测，例如销售额、新客、时间范围和过滤条件都应有明确依据。

第四，要严格限制模型只能使用已提供的表、字段和关联关系。信息不足时，应返回缺失项或请求澄清，而不是编造字段、口径或 JOIN 条件。

第五，Few-shot 和输出约束要服务于工程执行。示例应覆盖单表、多表、歧义和无法回答等场景；输出应采用固定 JSON
或其他结构化格式，便于程序解析、校验和失败重试。

此外，DataAgent 还需要设计错误反馈机制，将 SQL 执行错误、字段缺失或方言问题重新提供给模型进行定向修复。

总体来说，好的 DataAgent Prompt 不在于写得长，而在于任务单一、上下文完整、业务口径明确、约束清晰、输出可校验。

## 2、意图识别怎么做的，如何优化的呢？

我们在 Data Planner 中把意图识别和后续计划生成结合在一起，意图识别主要做了六方面优化。

第一，采用分层识别，而不是直接进行五分类。模型先判断用户是在提出独立问题，还是在承接上一轮进行追问。如果是独立问题，只分析当前输入；如果是追问，则结合历史问题、历史结果和计划，还原出完整需求，再识别为查数、探索性分析、确定性分析、报告解读或无关问题。这样能够解决“这些人呢”“再按品牌拆一下”等当前输入信息不完整的问题。

第二，重点明确容易混淆的类别边界。例如，单纯获取客观指标属于查数；用户提出分析目标但没有指定具体路径，属于探索性分析；用户明确给出步骤、输出格式或修改要求，属于确定性分析。报告解读则要求仅依赖已有报告即可回答，不能再补充或加工数据。通过明确判断依据，而不是只依赖“查询”“分析”等关键词，减少类别之间的混淆。

第三，对无关问题采用保守策略。因为误判为无关问题会直接拒绝用户，所以只拦截明确与数据分析无关或完全无法确定目标的问题。即使缺少日期、数据源或者具体处理方式，只要仍然可能属于数据需求，就先放行给后续节点处理，尽量降低误杀率。

第四，针对多轮追问增加上下文重构规则。追问不能只把最新一句话传给后续执行层，而是需要生成一份完整、自包含的新计划。例如上一轮已经查询出十个
SKU，用户再问毛利额时，如果这些 SKU 数量较少且结果不可稳定复现，就直接保留具体 SKU；如果上一轮是确定性的 TopN
筛选且结果数量很多，则复述筛选逻辑；如果上一轮是随机筛选，则需要明确引用上一轮实际结果。这样可以避免追问过程中查询范围丢失或发生漂移。

第五，使用正反 Few-shot 优化边界场景。除了提供每类意图的正常示例，还加入容易误判的反例，例如“GMV
环比并要求表格输出”虽然查询逻辑简单，但由于存在明确输出格式要求，应进入确定性分析；字段知识只用于帮助识别指标、维度和筛选条件，不能擅自把“秒送组”改写成某个具体字段值。Few-shot
的作用不仅是约束输出格式，更重要的是向模型展示类别边界和禁止行为。

第六，建立结构化约束和 Badcase 回归。意图识别结果会直接约束
scene、章节数量和计划粒度，例如查数只生成一个章节，探索性分析可以生成一到四个章节。线上出现误分类后，会按照“独立问题识别错误、追问上下文丢失、查数与分析混淆、探索性与确定性混淆、无关问题误杀”等类型归因，并将典型样本补充进回归集和
Few-shot。

整体上，我们并不是单独追求意图分类准确率，而是同时观察分类结果是否能生成正确、完整且可独立执行的计划。因为对于 DataAgent
来说，即使意图类别判断正确，如果时间、指标、筛选范围或上文实体没有被完整传递，最终任务仍然会执行错误。

## 3、对于DataAgent的badCase你是如何去分析和优化的呢？

对于 DataAgent 中出现的 Badcase，我通常按照“问题采集、链路定位、分类归因、针对性修复、回归验证”这套流程处理，而不是直接修改
Prompt。

首先，我会保留完整的执行 Trace，包括用户问题、多轮上下文、意图识别结果、知识召回结果、Schema 选择、Planner 计划、生成的
SQL、执行结果以及最终回答。然后寻找整条链路中第一个错误节点。因为 DataAgent 的错误会逐层传递，例如最终 SQL 查询错了，不一定是
SQL 模型能力不足，也可能是前面把指标识别错了、漏掉了筛选条件，或者选择了错误的数据表。

在分类上，我一般把 Badcase 分为几类。

第一类是意图和上下文理解问题，例如把查数问题识别成分析问题、把独立问题错误地当作追问，或者在“这些 SKU 的毛利额怎么样”这类追问中丢失上一轮的
SKU 范围。这类问题主要通过明确类别边界、增加多轮上下文重构、补充正反 Few-shot，以及输出结构化的 resolved query 来优化。

第二类是知识和 Schema 匹配问题，例如指标口径没有召回、字段描述不足、选择了错误的数据集，或者跨表分析时遗漏了关联表。这类问题通常不能只改
Prompt，而要完善表和字段元数据、指标别名、业务词典、逻辑外键，并优化 BM25、Embedding、RRF 和 reranker 等召回链路。

第三类是 Planner 问题，例如步骤遗漏、过度拆解、擅自增加分析逻辑，或者每个步骤不能独立执行。针对这类问题，我们会强化原子化、自包含和忠实原文约束。例如筛选与计算应该写在同一个步骤中，不能把“筛选品牌
A 的 SKU 并计算 GMV”拆成两个无法共享中间结果的步骤。

第四类是 SQL 问题，包括字段或表不存在、聚合方式错误、时间条件错误、JOIN 导致数据膨胀、数据库方言不兼容等。这类问题会结合语义模型、SQL
AST 校验、字段存在性检查、执行错误定向重试和结果一致性检查进行优化，而不是让模型无约束地反复生成 SQL。

第五类是结果生成和展示问题，例如 SQL
数据正确，但模型在总结时修改了数值、结论没有依据、百分比格式错误，或者图表与用户要求不一致。这类问题需要限制模型只能基于查询结果生成结论，并增加数值一致性校验和展示层格式处理。

每次修复之后，我会把该 Badcase 加入固定回归集，同时测试相邻场景，避免为了解决一个问题造成新的退化。例如增加“存在表格要求就识别为确定性分析”的规则后，还需要检查普通查数问题是否被大面积错误升级为分析任务。

我对 Badcase 分析最大的心得有三个。

第一，必须定位第一个错误节点。最终答案错误只是结果，真正的原因可能发生在很早的意图识别、知识召回或 Schema 选择阶段。

第二，SQL 能执行不代表结果正确。DataAgent 更应该关注指标口径、筛选条件和最终数据结果是否一致，而不能只看 SQL 执行成功率。

第三，Badcase 不能只靠不断增加 Prompt 解决。稳定规则适合放到代码和语义层，业务口径适合沉淀到知识库，语义歧义交给模型处理，执行错误则通过校验和重试机制解决。需要根据问题类型选择合适的修复位置。

因此，我认为 DataAgent 的 Badcase 优化本质上是一套数据飞轮：通过线上 Trace
和用户反馈发现问题，进行分层归因，把问题修复到正确的节点，再沉淀到回归评测集，持续验证整体链路是否真正提升。

第四，要严格限制模型只能使用已提供的表、字段和关联关系。信息不足时，应返回缺失项或请求澄清，而不是编造字段、口径或 JOIN 条件。

第五，Few-shot 和输出约束要服务于工程执行。示例应覆盖单表、多表、歧义和无法回答等场景；输出应采用固定 JSON
或其他结构化格式，便于程序解析、校验和失败重试。

此外，DataAgent 还需要设计错误反馈机制，将 SQL 执行错误、字段缺失或方言问题重新提供给模型进行定向修复。

总体来说，好的 DataAgent Prompt 不在于写得长，而在于任务单一、上下文完整、业务口径明确、约束清晰、输出可校验。

## 4.如何选择不同的向量数据库呢？
我对向量数据库的理解是，它并不负责把文本转换成向量，向量化通常由 Embedding 模型完成。向量数据库主要负责存储向量及其关联的原始内容、元数据，并通过近似最近邻算法完成高效的相似度检索，同时提供过滤、更新、删除、持久化、分片和高可用等数据库能力。

目前主流的方案可以分为三类。

第一类是 Milvus、Qdrant、Weaviate、Pinecone 这样的专业向量数据库。Milvus 是开源的分布式向量数据库，支持 HNSW、IVF、DiskANN 等多种索引，比较适合数据规模较大、并发较高，并且要求私有化部署的场景。Qdrant 对向量检索和元数据过滤结合得比较好，适合 RAG 中按照用户、知识库、文档类型等条件进行过滤。Weaviate 原生支持向量检索、BM25 和混合检索。Pinecone 主要是托管式服务，开发和运维成本相对低，但需要考虑云服务成本以及数据部署要求。

第二类是 Elasticsearch 和 pgvector，即在已有搜索引擎或关系数据库上增加向量能力。Elasticsearch 既支持传统关键词检索，也支持 dense_vector 和近似 KNN 检索，所以比较适合同时需要 BM25、向量召回、条件过滤和混合搜索的知识库场景。pgvector 是 PostgreSQL 的向量扩展，优势是向量和原有业务数据可以放在同一个数据库中，能够继续使用 SQL、事务和关系查询，适合数据规模中小、已经大量使用 PostgreSQL 的系统。

第三类是 FAISS 这样的向量检索库。FAISS 支持 Flat、IVF、HNSW、PQ 等算法，单机检索性能很好，也支持 GPU，但它本质上是一个相似度检索和聚类库，不是完整的数据库。持久化、分布式、权限、元数据过滤、高可用和数据更新等能力通常需要业务系统自己实现。

在索引算法方面，我主要了解 Flat、HNSW、IVF 和 PQ。Flat 是精确暴力检索，召回率最高，但数据量大时速度较慢；HNSW 基于图结构，通常能够获得比较好的延迟和召回率，但索引会占用较多内存，构建成本也比较高；IVF 会先对向量进行聚类，查询时只搜索部分倒排分区，更适合大规模数据，但需要在检索速度和召回率之间调节参数；PQ 会对向量进行压缩，能够降低内存和存储占用，但会损失一定精度。比如 pgvector 同时支持 HNSW 和 IVFFlat，HNSW 一般查询性能更好，而 IVFFlat 构建更快、内存占用更低。

真正做选型时，我不会简单判断哪一个数据库最好，而是会看数据规模、向量维度、QPS、P95 和 P99 延迟、Recall@K、更新频率、过滤条件复杂度、是否需要 BM25 混合检索、是否要求私有化部署，以及团队已有的技术栈和运维成本。

例如在知识库或者 DataAgent 项目中，如果系统原本已经使用 Elasticsearch，而且既需要关键词精确召回，又需要语义召回和元数据过滤，我会优先考虑 Elasticsearch，通过 BM25 和向量检索产生候选结果，再使用 RRF 或 reranker 进行融合和精排。向量规模进一步扩大、向量检索成为系统主要负载时，可以考虑把专业向量检索迁移到 Milvus；如果业务数据原本就在 PostgreSQL 中，而且数据规模和并发不大，则可以优先考虑 pgvector，避免额外维护一套数据库。

所以我认为向量数据库选型的核心，不只是比较单次向量检索速度，而是综合考虑召回效果、过滤能力、数据更新、系统稳定性和整体工程成本。

## 6.对于Multi-Agent，你们为什么选择这样的架构呢？
当前项目选择 Multi-agent，并不是为了单纯增加 Agent 数量，而是因为数据分析任务本身具有明显的分阶段和异构特征。系统既要处理快速问数、BI 请求，也要处理多步骤分析、报告生成和探索任务，因此入口先由 data_agent 做轻量路由：快速问数走 SQL Agent，BI 请求走 BI Proxy，复杂分析才进入 master_agent。进入主链路后，再把“理解和规划、任务调度、数据处理、结果总结”拆开，避免一个 Agent 同时承担所有职责。

在复杂分析中，data_planner 只负责把用户问题、数据描述和知识整理成带依赖关系的 GraphPlan；data_executer 只负责根据依赖调度节点、控制并发和更新状态；每个节点再交给 process_expert → Text取数Agent 完成取数、代码计算和工具调用；节点总结、可视化以及最终的 Chat/HTML 报告分别由总结 Agent 负责。这样每个 Agent 可以使用更聚焦的 Prompt、模型和工具集合，减少单 Agent 同时面对大量工具时的选择混乱，也能实现节点级重试、失败隔离、并行执行、过程观测和人工确认。

如果全部交给一个 Agent，规划、取数、计算和总结会混在一次超长上下文里。一旦某一步失败，很难只重跑失败节点；增加一种工具或业务场景也容易影响整个 Prompt。Multi-agent 架构让能力边界更加清晰，新场景可以通过新增路由、专业 Agent 或 Tool 扩展，而不必整体重写主 Agent。

同时，这种架构也有明确代价：Agent 间调用会增加模型请求、网络耗时和上下文传递复杂度，首 token 时间通常比单 Agent 更高。因此当前项目采用的原则应该概括为：

简单任务走快速路径，复杂任务才走 Multi-agent；

已有结构化计划时跳过 planner；

只有具备依赖关系和专业分工的任务才进入完整执行链。

这也是当前仍需要继续优化的地方，例如配置化 Report、direct_execute 等已有明确计划的场景，可以跳过不必要的系统知识和 few-shot 召回，避免为了架构完整而付出无意义的延迟。

## 7.评测的时候，你认为Multi-Agent和单Agent评测起来有什么不同呢？
核心区别可以概括为一句话：单 Agent 像调试一个大函数，Multi-agent 更像调试一个分布式工作流。

| 维度 | 单 Agent | Multi-agent |
| -- | -- | -- |
| 故障定位 | 主要检查 Prompt、模型输出和工具调用 | 还要检查路由、上下文传递、计划、节点调度和结果聚合 |
| 日志方式 | 一次请求的一条调用链基本够用 | 必须通过 `trace_id + node_id + caller/callee` 串起完整链路 |
| 问题复现 | 固定输入、Prompt 和模型参数即可 | 还需固定中间计划、节点结果、并发顺序和共享状态 |
| 评估对象 | 主要评价最终回答 | 同时评价每个 Agent、Agent 间交接以及最终结果 |
| 性能评估 | 关注整体延迟、Token 和成本 | 还要分析各节点耗时、关键路径、并发收益和冗余调用 |
| 稳定性 | 失败通常集中在一次推理内 | 一个上游错误可能被下游不断放大 |

对于当前项目，调试时不能只看最终报告，而要沿着真实链路逐层定位：

```text
data_agent
  路由是否正确
    ↓
pre_process_clarifier
  query、数据描述、知识是否正确写入 shared_data
    ↓
data_planner
  GraphPlan 是否覆盖用户要求，依赖关系是否合理
    ↓
data_executer
  节点是否按依赖启动，并发、重试和状态是否正确
    ↓
Text取数Agent / Tools
  SQL、Python、指标计算和原始数据是否正确
    ↓
node/global summary
  是否忠实使用上游结果，有没有遗漏或编造
```

例如最终报告里的数字错误，可能来自四个位置：planner 规划错了计算口径、执行 Agent 选择了错误工具、工具本身计算错误，或者总结 Agent 抄错了正确结果。只看最终输出无法判断，所以 Multi-agent 必须保存中间产物，包括 planner 的 `GraphPlan`、每个节点的输入输出、工具请求与原始结果、状态变更和最终汇总依据。

评估方式也要从“只评最终答案”变成三层：

- 组件评估：路由准确率、知识召回相关性、计划覆盖度、依赖正确性、工具调用正确率、节点数值准确性、总结忠实度。
- 协作评估：上下文是否完整传递、Agent 是否重复劳动、是否出现循环调用、上游错误能否被识别、失败节点能否独立恢复。
- 端到端评估：最终任务成功率、数值正确率、用户要求覆盖率、首 token、总耗时、Token 成本和调用次数。

Multi-agent 还需要“固定中间结果”的隔离评估。例如固定一份正确 `GraphPlan` 只测试 executor，可以判断问题是否在执行阶段；固定工具返回只测试 summary，可以判断是否发生总结失真；固定 planner 输入测试不同知识召回结果，可以判断知识是否干扰计划。这种分段回放是单 Agent 评估中不太突出、但 Multi-agent 必须具备的能力。

Multi-agent 的优点是边界清晰后更容易精确定位问题，但前提是链路观测完整；如果没有统一 trace、中间状态和可回放能力，它反而会比单 Agent 更难调试。

## 8.你理解的当前项目的harness是如何做的呢？
我理解的 Agent Harness，不是某个 Agent，也不只是工作流编排，而是包裹在模型外面的一整套运行和约束环境。它决定模型能看到什么上下文、能调用哪些工具、按照什么协议行动、失败后如何重试或降级，以及整个过程如何被追踪、回放和评估。Workflow 描述业务上“先做什么、后做什么”，Orchestration 负责节点调度，而 Harness 覆盖得更广，包含上下文、工具、执行循环、状态、可靠性和可观测性。相同的模型放在不同 Harness 里，最终效果可能差别很大。

在当前项目里，我们的 Harness 不是集中在一个文件中，而是构建在 Oxygent 运行时和业务工作流之上。入口层由 data_agent 根据请求类型路由到 SQL、BI 或复杂分析链路；复杂任务进入 master_agent 后，预处理阶段把用户问题、数据集元数据、知识召回、Few-shot、时间信息和历史对话整理到统一的 OxyRequest.shared_data 中。这样后面的 Planner、Executor 和专业 Agent 使用的是同一套上下文，而不是各自重新理解请求。

执行层通过结构化协议降低多 Agent 协作的不确定性。Planner 不能随意输出一段自然语言计划，而是要生成包含步骤、依赖关系和执行指令的 GraphPlan；Executor 再根据 DAG 依赖划分执行批次，控制并发，调用 process_and_summary_agent，并通过 update_plan 更新执行状态。具体的数据获取、Python 加工、指标分析和 Web 搜索被限制在 Text取数Agent 等专业 Agent 中，最后由节点总结和全局总结 Agent 负责输出。这相当于把“理解问题、制定计划、执行取数、形成结论”拆成了有明确输入输出边界的运行契约。

可靠性和可观测性也是 Harness 的重要部分。项目统一配置了工具权限、最大 ReAct 轮数、超时、重试和备用模型；前端可以收到计划、步骤、进度、思考和答案等流式消息；每次调用通过 trace_id、node_id 和调用栈串联，并把节点输入、输出和共享状态写入 ES。出现问题时，可以判断错误发生在知识召回、规划、任务调度、取数还是总结阶段；重跑时还可以复用前置节点缓存，只重新执行指定步骤之后的链路。

不过要区分“运行时 Harness”和“评测 Harness”。当前项目的运行时 Harness 已经比较完整，也有 judge_tool 这样的在线自检机制；但系统化的离线评测 Harness 还需要继续补齐。理想状态是沉淀一批固定数据快照和标准案例，能够固定 Planner 输出单测 Executor，固定工具结果单测 Summary，并分别评估路由准确率、计划合法性、SQL 与数据正确性、总结忠实度，以及端到端成功率、首 Token、总耗时和成本。这样每次修改 Prompt、模型或工具后，都能利用历史 Trace 回放并进行回归对比。

最后可以用一句话收束：

我们做 Harness 的核心，不是把多个 Agent 连起来，而是给这些具有随机性的 Agent 建立统一的上下文、能力边界、执行协议、容错机制和追踪评测体系，让系统从“偶尔能跑通”变成“可控制、可定位、可回放、可持续迭代”。
