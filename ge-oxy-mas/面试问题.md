# 面试问题
## 1、对于prompt的内容，哪种形式更好呢？

对于 DataAgent，我认为好的 Prompt 主要有以下几点。

第一，任务边界要明确。需要说明当前 Prompt 负责的是意图识别、Schema 选择、SQL 生成还是结果分析，并明确禁止事项，避免一个 Prompt
承担过多职责。

第二，输入信息要完整且结构化。除了用户问题，还应提供表和字段描述、字段类型、样例值、主外键关系、数据库方言、指标口径和业务知识，并用固定标签区分不同内容。

第三，业务语义和数据口径要清晰。模型应优先使用已提供的指标定义和语义模型，不能根据字段名自行猜测，例如销售额、新客、时间范围和过滤条件都应有明确依据。

第四，要严格限制模型只能使用已提供的表、字段和关联关系。信息不足时，应返回缺失项或请求澄清，而不是编造字段、口径或 JOIN 条件。

第五，Few-shot 和输出约束要服务于工程执行。示例应覆盖单表、多表、歧义和无法回答等场景；输出应采用固定 JSON
或其他结构化格式，便于程序解析、校验和失败重试。

此外，DataAgent 还需要设计错误反馈机制，将 SQL 执行错误、字段缺失或方言问题重新提供给模型进行定向修复。

总体来说，好的 DataAgent Prompt 不在于写得长，而在于任务单一、上下文完整、业务口径明确、约束清晰、输出可校验。

## 2、意图识别怎么做的，如何优化的呢？

我们在 Data Planner 中把意图识别和后续计划生成结合在一起，意图识别主要做了六方面优化。

第一，采用分层识别，而不是直接进行五分类。模型先判断用户是在提出独立问题，还是在承接上一轮进行追问。如果是独立问题，只分析当前输入；如果是追问，则结合历史问题、历史结果和计划，还原出完整需求，再识别为查数、探索性分析、确定性分析、报告解读或无关问题。这样能够解决“这些人呢”“再按品牌拆一下”等当前输入信息不完整的问题。

第二，重点明确容易混淆的类别边界。例如，单纯获取客观指标属于查数；用户提出分析目标但没有指定具体路径，属于探索性分析；用户明确给出步骤、输出格式或修改要求，属于确定性分析。报告解读则要求仅依赖已有报告即可回答，不能再补充或加工数据。通过明确判断依据，而不是只依赖“查询”“分析”等关键词，减少类别之间的混淆。

第三，对无关问题采用保守策略。因为误判为无关问题会直接拒绝用户，所以只拦截明确与数据分析无关或完全无法确定目标的问题。即使缺少日期、数据源或者具体处理方式，只要仍然可能属于数据需求，就先放行给后续节点处理，尽量降低误杀率。

第四，针对多轮追问增加上下文重构规则。追问不能只把最新一句话传给后续执行层，而是需要生成一份完整、自包含的新计划。例如上一轮已经查询出十个
SKU，用户再问毛利额时，如果这些 SKU 数量较少且结果不可稳定复现，就直接保留具体 SKU；如果上一轮是确定性的 TopN
筛选且结果数量很多，则复述筛选逻辑；如果上一轮是随机筛选，则需要明确引用上一轮实际结果。这样可以避免追问过程中查询范围丢失或发生漂移。

第五，使用正反 Few-shot 优化边界场景。除了提供每类意图的正常示例，还加入容易误判的反例，例如“GMV
环比并要求表格输出”虽然查询逻辑简单，但由于存在明确输出格式要求，应进入确定性分析；字段知识只用于帮助识别指标、维度和筛选条件，不能擅自把“秒送组”改写成某个具体字段值。Few-shot
的作用不仅是约束输出格式，更重要的是向模型展示类别边界和禁止行为。

第六，建立结构化约束和 Badcase 回归。意图识别结果会直接约束
scene、章节数量和计划粒度，例如查数只生成一个章节，探索性分析可以生成一到四个章节。线上出现误分类后，会按照“独立问题识别错误、追问上下文丢失、查数与分析混淆、探索性与确定性混淆、无关问题误杀”等类型归因，并将典型样本补充进回归集和
Few-shot。

整体上，我们并不是单独追求意图分类准确率，而是同时观察分类结果是否能生成正确、完整且可独立执行的计划。因为对于 DataAgent
来说，即使意图类别判断正确，如果时间、指标、筛选范围或上文实体没有被完整传递，最终任务仍然会执行错误。

## 3、对于DataAgent的badCase你是如何去分析和优化的呢？

对于 DataAgent 中出现的 Badcase，我通常按照“问题采集、链路定位、分类归因、针对性修复、回归验证”这套流程处理，而不是直接修改
Prompt。

首先，我会保留完整的执行 Trace，包括用户问题、多轮上下文、意图识别结果、知识召回结果、Schema 选择、Planner 计划、生成的
SQL、执行结果以及最终回答。然后寻找整条链路中第一个错误节点。因为 DataAgent 的错误会逐层传递，例如最终 SQL 查询错了，不一定是
SQL 模型能力不足，也可能是前面把指标识别错了、漏掉了筛选条件，或者选择了错误的数据表。

在分类上，我一般把 Badcase 分为几类。

第一类是意图和上下文理解问题，例如把查数问题识别成分析问题、把独立问题错误地当作追问，或者在“这些 SKU 的毛利额怎么样”这类追问中丢失上一轮的
SKU 范围。这类问题主要通过明确类别边界、增加多轮上下文重构、补充正反 Few-shot，以及输出结构化的 resolved query 来优化。

第二类是知识和 Schema 匹配问题，例如指标口径没有召回、字段描述不足、选择了错误的数据集，或者跨表分析时遗漏了关联表。这类问题通常不能只改
Prompt，而要完善表和字段元数据、指标别名、业务词典、逻辑外键，并优化 BM25、Embedding、RRF 和 reranker 等召回链路。

第三类是 Planner 问题，例如步骤遗漏、过度拆解、擅自增加分析逻辑，或者每个步骤不能独立执行。针对这类问题，我们会强化原子化、自包含和忠实原文约束。例如筛选与计算应该写在同一个步骤中，不能把“筛选品牌
A 的 SKU 并计算 GMV”拆成两个无法共享中间结果的步骤。

第四类是 SQL 问题，包括字段或表不存在、聚合方式错误、时间条件错误、JOIN 导致数据膨胀、数据库方言不兼容等。这类问题会结合语义模型、SQL
AST 校验、字段存在性检查、执行错误定向重试和结果一致性检查进行优化，而不是让模型无约束地反复生成 SQL。

第五类是结果生成和展示问题，例如 SQL
数据正确，但模型在总结时修改了数值、结论没有依据、百分比格式错误，或者图表与用户要求不一致。这类问题需要限制模型只能基于查询结果生成结论，并增加数值一致性校验和展示层格式处理。

每次修复之后，我会把该 Badcase 加入固定回归集，同时测试相邻场景，避免为了解决一个问题造成新的退化。例如增加“存在表格要求就识别为确定性分析”的规则后，还需要检查普通查数问题是否被大面积错误升级为分析任务。

我对 Badcase 分析最大的心得有三个。

第一，必须定位第一个错误节点。最终答案错误只是结果，真正的原因可能发生在很早的意图识别、知识召回或 Schema 选择阶段。

第二，SQL 能执行不代表结果正确。DataAgent 更应该关注指标口径、筛选条件和最终数据结果是否一致，而不能只看 SQL 执行成功率。

第三，Badcase 不能只靠不断增加 Prompt 解决。稳定规则适合放到代码和语义层，业务口径适合沉淀到知识库，语义歧义交给模型处理，执行错误则通过校验和重试机制解决。需要根据问题类型选择合适的修复位置。

因此，我认为 DataAgent 的 Badcase 优化本质上是一套数据飞轮：通过线上 Trace
和用户反馈发现问题，进行分层归因，把问题修复到正确的节点，再沉淀到回归评测集，持续验证整体链路是否真正提升。

第四，要严格限制模型只能使用已提供的表、字段和关联关系。信息不足时，应返回缺失项或请求澄清，而不是编造字段、口径或 JOIN 条件。

第五，Few-shot 和输出约束要服务于工程执行。示例应覆盖单表、多表、歧义和无法回答等场景；输出应采用固定 JSON
或其他结构化格式，便于程序解析、校验和失败重试。

此外，DataAgent 还需要设计错误反馈机制，将 SQL 执行错误、字段缺失或方言问题重新提供给模型进行定向修复。

总体来说，好的 DataAgent Prompt 不在于写得长，而在于任务单一、上下文完整、业务口径明确、约束清晰、输出可校验。

## 4.如何选择不同的向量数据库呢？
我对向量数据库的理解是，它并不负责把文本转换成向量，向量化通常由 Embedding 模型完成。向量数据库主要负责存储向量及其关联的原始内容、元数据，并通过近似最近邻算法完成高效的相似度检索，同时提供过滤、更新、删除、持久化、分片和高可用等数据库能力。

目前主流的方案可以分为三类。

第一类是 Milvus、Qdrant、Weaviate、Pinecone 这样的专业向量数据库。Milvus 是开源的分布式向量数据库，支持 HNSW、IVF、DiskANN 等多种索引，比较适合数据规模较大、并发较高，并且要求私有化部署的场景。Qdrant 对向量检索和元数据过滤结合得比较好，适合 RAG 中按照用户、知识库、文档类型等条件进行过滤。Weaviate 原生支持向量检索、BM25 和混合检索。Pinecone 主要是托管式服务，开发和运维成本相对低，但需要考虑云服务成本以及数据部署要求。

第二类是 Elasticsearch 和 pgvector，即在已有搜索引擎或关系数据库上增加向量能力。Elasticsearch 既支持传统关键词检索，也支持 dense_vector 和近似 KNN 检索，所以比较适合同时需要 BM25、向量召回、条件过滤和混合搜索的知识库场景。pgvector 是 PostgreSQL 的向量扩展，优势是向量和原有业务数据可以放在同一个数据库中，能够继续使用 SQL、事务和关系查询，适合数据规模中小、已经大量使用 PostgreSQL 的系统。

第三类是 FAISS 这样的向量检索库。FAISS 支持 Flat、IVF、HNSW、PQ 等算法，单机检索性能很好，也支持 GPU，但它本质上是一个相似度检索和聚类库，不是完整的数据库。持久化、分布式、权限、元数据过滤、高可用和数据更新等能力通常需要业务系统自己实现。

在索引算法方面，我主要了解 Flat、HNSW、IVF 和 PQ。Flat 是精确暴力检索，召回率最高，但数据量大时速度较慢；HNSW 基于图结构，通常能够获得比较好的延迟和召回率，但索引会占用较多内存，构建成本也比较高；IVF 会先对向量进行聚类，查询时只搜索部分倒排分区，更适合大规模数据，但需要在检索速度和召回率之间调节参数；PQ 会对向量进行压缩，能够降低内存和存储占用，但会损失一定精度。比如 pgvector 同时支持 HNSW 和 IVFFlat，HNSW 一般查询性能更好，而 IVFFlat 构建更快、内存占用更低。

真正做选型时，我不会简单判断哪一个数据库最好，而是会看数据规模、向量维度、QPS、P95 和 P99 延迟、Recall@K、更新频率、过滤条件复杂度、是否需要 BM25 混合检索、是否要求私有化部署，以及团队已有的技术栈和运维成本。

例如在知识库或者 DataAgent 项目中，如果系统原本已经使用 Elasticsearch，而且既需要关键词精确召回，又需要语义召回和元数据过滤，我会优先考虑 Elasticsearch，通过 BM25 和向量检索产生候选结果，再使用 RRF 或 reranker 进行融合和精排。向量规模进一步扩大、向量检索成为系统主要负载时，可以考虑把专业向量检索迁移到 Milvus；如果业务数据原本就在 PostgreSQL 中，而且数据规模和并发不大，则可以优先考虑 pgvector，避免额外维护一套数据库。

所以我认为向量数据库选型的核心，不只是比较单次向量检索速度，而是综合考虑召回效果、过滤能力、数据更新、系统稳定性和整体工程成本。

## 6.对于Multi-Agent，你们为什么选择这样的架构呢？
当前项目选择 Multi-agent，并不是为了单纯增加 Agent 数量，而是因为数据分析任务本身具有明显的分阶段和异构特征。系统既要处理快速问数、BI 请求，也要处理多步骤分析、报告生成和探索任务，因此入口先由 data_agent 做轻量路由：快速问数走 SQL Agent，BI 请求走 BI Proxy，复杂分析才进入 master_agent。进入主链路后，再把“理解和规划、任务调度、数据处理、结果总结”拆开，避免一个 Agent 同时承担所有职责。

在复杂分析中，data_planner 只负责把用户问题、数据描述和知识整理成带依赖关系的 GraphPlan；data_executer 只负责根据依赖调度节点、控制并发和更新状态；每个节点再交给 process_expert → Text取数Agent 完成取数、代码计算和工具调用；节点总结、可视化以及最终的 Chat/HTML 报告分别由总结 Agent 负责。这样每个 Agent 可以使用更聚焦的 Prompt、模型和工具集合，减少单 Agent 同时面对大量工具时的选择混乱，也能实现节点级重试、失败隔离、并行执行、过程观测和人工确认。

如果全部交给一个 Agent，规划、取数、计算和总结会混在一次超长上下文里。一旦某一步失败，很难只重跑失败节点；增加一种工具或业务场景也容易影响整个 Prompt。Multi-agent 架构让能力边界更加清晰，新场景可以通过新增路由、专业 Agent 或 Tool 扩展，而不必整体重写主 Agent。

同时，这种架构也有明确代价：Agent 间调用会增加模型请求、网络耗时和上下文传递复杂度，首 token 时间通常比单 Agent 更高。因此当前项目采用的原则应该概括为：

简单任务走快速路径，复杂任务才走 Multi-agent；

已有结构化计划时跳过 planner；

只有具备依赖关系和专业分工的任务才进入完整执行链。

这也是当前仍需要继续优化的地方，例如配置化 Report、direct_execute 等已有明确计划的场景，可以跳过不必要的系统知识和 few-shot 召回，避免为了架构完整而付出无意义的延迟。

## 7.评测的时候，你认为Multi-Agent和单Agent评测起来有什么不同呢？
核心区别可以概括为一句话：单 Agent 像调试一个大函数，Multi-agent 更像调试一个分布式工作流。

| 维度 | 单 Agent | Multi-agent |
| -- | -- | -- |
| 故障定位 | 主要检查 Prompt、模型输出和工具调用 | 还要检查路由、上下文传递、计划、节点调度和结果聚合 |
| 日志方式 | 一次请求的一条调用链基本够用 | 必须通过 `trace_id + node_id + caller/callee` 串起完整链路 |
| 问题复现 | 固定输入、Prompt 和模型参数即可 | 还需固定中间计划、节点结果、并发顺序和共享状态 |
| 评估对象 | 主要评价最终回答 | 同时评价每个 Agent、Agent 间交接以及最终结果 |
| 性能评估 | 关注整体延迟、Token 和成本 | 还要分析各节点耗时、关键路径、并发收益和冗余调用 |
| 稳定性 | 失败通常集中在一次推理内 | 一个上游错误可能被下游不断放大 |

对于当前项目，调试时不能只看最终报告，而要沿着真实链路逐层定位：

```text
data_agent
  路由是否正确
    ↓
pre_process_clarifier
  query、数据描述、知识是否正确写入 shared_data
    ↓
data_planner
  GraphPlan 是否覆盖用户要求，依赖关系是否合理
    ↓
data_executer
  节点是否按依赖启动，并发、重试和状态是否正确
    ↓
Text取数Agent / Tools
  SQL、Python、指标计算和原始数据是否正确
    ↓
node/global summary
  是否忠实使用上游结果，有没有遗漏或编造
```

例如最终报告里的数字错误，可能来自四个位置：planner 规划错了计算口径、执行 Agent 选择了错误工具、工具本身计算错误，或者总结 Agent 抄错了正确结果。只看最终输出无法判断，所以 Multi-agent 必须保存中间产物，包括 planner 的 `GraphPlan`、每个节点的输入输出、工具请求与原始结果、状态变更和最终汇总依据。

评估方式也要从“只评最终答案”变成三层：

- 组件评估：路由准确率、知识召回相关性、计划覆盖度、依赖正确性、工具调用正确率、节点数值准确性、总结忠实度。
- 协作评估：上下文是否完整传递、Agent 是否重复劳动、是否出现循环调用、上游错误能否被识别、失败节点能否独立恢复。
- 端到端评估：最终任务成功率、数值正确率、用户要求覆盖率、首 token、总耗时、Token 成本和调用次数。

Multi-agent 还需要“固定中间结果”的隔离评估。例如固定一份正确 `GraphPlan` 只测试 executor，可以判断问题是否在执行阶段；固定工具返回只测试 summary，可以判断是否发生总结失真；固定 planner 输入测试不同知识召回结果，可以判断知识是否干扰计划。这种分段回放是单 Agent 评估中不太突出、但 Multi-agent 必须具备的能力。

Multi-agent 的优点是边界清晰后更容易精确定位问题，但前提是链路观测完整；如果没有统一 trace、中间状态和可回放能力，它反而会比单 Agent 更难调试。

## 8.你理解的当前项目的harness是如何做的呢？
我理解的 Agent Harness，不是某个 Agent，也不只是工作流编排，而是包裹在模型外面的一整套运行和约束环境。它决定模型能看到什么上下文、能调用哪些工具、按照什么协议行动、失败后如何重试或降级，以及整个过程如何被追踪、回放和评估。Workflow 描述业务上“先做什么、后做什么”，Orchestration 负责节点调度，而 Harness 覆盖得更广，包含上下文、工具、执行循环、状态、可靠性和可观测性。相同的模型放在不同 Harness 里，最终效果可能差别很大。

在当前项目里，我们的 Harness 不是集中在一个文件中，而是构建在 Oxygent 运行时和业务工作流之上。入口层由 data_agent 根据请求类型路由到 SQL、BI 或复杂分析链路；复杂任务进入 master_agent 后，预处理阶段把用户问题、数据集元数据、知识召回、Few-shot、时间信息和历史对话整理到统一的 OxyRequest.shared_data 中。这样后面的 Planner、Executor 和专业 Agent 使用的是同一套上下文，而不是各自重新理解请求。

执行层通过结构化协议降低多 Agent 协作的不确定性。Planner 不能随意输出一段自然语言计划，而是要生成包含步骤、依赖关系和执行指令的 GraphPlan；Executor 再根据 DAG 依赖划分执行批次，控制并发，调用 process_and_summary_agent，并通过 update_plan 更新执行状态。具体的数据获取、Python 加工、指标分析和 Web 搜索被限制在 Text取数Agent 等专业 Agent 中，最后由节点总结和全局总结 Agent 负责输出。这相当于把“理解问题、制定计划、执行取数、形成结论”拆成了有明确输入输出边界的运行契约。

可靠性和可观测性也是 Harness 的重要部分。项目统一配置了工具权限、最大 ReAct 轮数、超时、重试和备用模型；前端可以收到计划、步骤、进度、思考和答案等流式消息；每次调用通过 trace_id、node_id 和调用栈串联，并把节点输入、输出和共享状态写入 ES。出现问题时，可以判断错误发生在知识召回、规划、任务调度、取数还是总结阶段；重跑时还可以复用前置节点缓存，只重新执行指定步骤之后的链路。

不过要区分“运行时 Harness”和“评测 Harness”。当前项目的运行时 Harness 已经比较完整，也有 judge_tool 这样的在线自检机制；但系统化的离线评测 Harness 还需要继续补齐。理想状态是沉淀一批固定数据快照和标准案例，能够固定 Planner 输出单测 Executor，固定工具结果单测 Summary，并分别评估路由准确率、计划合法性、SQL 与数据正确性、总结忠实度，以及端到端成功率、首 Token、总耗时和成本。这样每次修改 Prompt、模型或工具后，都能利用历史 Trace 回放并进行回归对比。

最后可以用一句话收束：

我们做 Harness 的核心，不是把多个 Agent 连起来，而是给这些具有随机性的 Agent 建立统一的上下文、能力边界、执行协议、容错机制和追踪评测体系，让系统从“偶尔能跑通”变成“可控制、可定位、可回放、可持续迭代”。

## 9. Planner Agent 的 Prompt 是如何设计、约束和评测的？

### 9.1 核心职责

Planner 不负责真正取数，而是把用户问题、历史对话、数据摘要和业务知识转换成结构化的 `GraphPlan`，再交给 Executor 执行。

```text
理解用户需求
    ↓
识别任务类型
    ↓
生成步骤及依赖关系
    ↓
输出 GraphPlan
```

### 9.2 Prompt 涉及哪些方面

| 方面 | Prompt 要求 |
| -- | -- |
| 问题类型 | 先区分独立问题和追问；追问需要结合历史信息，重新生成完整计划 |
| 意图分类 | AUTO 和 REPORT 包含查数、探索性分析、确定性分析、报告解读、无关问题 |
| 模式差异 | DEEP_RESEARCH 不单独保留查数类型，而是将其归入确定性分析 |
| 需求保留 | 时间、指标、筛选条件、粒度、公式、方法和输出形式都要写入计划 |
| 步骤设计 | 每一步都要包含实际的数据查询或处理，并且能够独立理解和执行 |
| 图结构 | 输出步骤 ID、步骤内容和依赖关系，支持串行、并行、分叉和汇聚 |

### 9.3 如何约束 Planner

Planner 的约束不是只靠一句“不要编造”，而是通过角色和任务定义、意图边界、执行铁律、结构化 Schema、正反 Few-shot、输出协议六层共同完成。

| 约束层 | 主要作用 |
| -- | -- |
| 角色与核心任务 | 把 Planner 限定为“需求到 GraphPlan 的映射器”，不负责自由分析和真正取数 |
| 意图识别规则 | 约束 `scene` 的判断边界，以及不同意图允许生成多少步骤 |
| 执行铁律 | 约束需求保留、步骤粒度、时间处理、知识使用和追问合并 |
| Schema 与图规则 | 约束字段、步骤数量、ID 和依赖关系 |
| Notes 与 Few-shot | 用正确示例和错误示例补充容易误判的边界 |
| 输出协议 | 约束只能输出可解析的工具调用 JSON |

需要区分两种“硬约束”：Prompt 中使用“必须、严禁”表达的规则属于模型侧硬约束；Planner 代码当前直接校验的主要是 JSON 能否解析以及是否存在 `tool_name`。步骤数、循环依赖、需求遗漏等规则仍需要评测器或后续校验补强，不能因为写进 Prompt 就认为已经百分之百保证。

#### 9.3.1 独立问题和多轮追问约束

| 场景 | 约束方式 |
| -- | -- |
| 独立新问题 | 只分析当前输入，不继承无关的历史任务 |
| 连续追加要求 | 第一轮做 A、第二轮补 B、第三轮补 C，第三轮必须重新生成包含 A、B、C 的完整计划 |
| 修改分析对象 | 原计划对甲执行 A、B、C，用户把甲改成乙，新计划应对乙执行完整的 A、B、C |
| 切换到无关新任务 | 新对象和新动作与前文没有明确关系时，应视为独立问题，不能强行拼接历史计划 |
| 使用上一轮结果 | 少量且无法稳定复现的结果应直接枚举实际值；大量但可确定复现的 TopN 结果应复述筛选逻辑 |
| 完整标识 | 人名和 ERP、商品名和 ID 等组合标识不能截断，必须完整传给后续步骤 |

每次 `make_graph_plan` 都会产生一份独立计划，因此追问不能只生成增量步骤。最新计划必须完整、自包含，后续 Executor 不需要回看 Planner 的思考过程，也能知道完整的分析对象、条件和动作。

#### 9.3.2 意图和 `scene` 约束

| 意图 | 判断边界 | 计划约束 |
| -- | -- | -- |
| 查数 | 获取客观指标，允许简单加工，但没有表格、图表等复杂输出要求 | `scene="查数"`；仅 1 个步骤；尽量保留用户原话作为 `detail`；`output=""`；禁止发散 |
| 探索性分析 | 用户给出了分析目标，但没有规定具体路径，合理路径通常不唯一 | `scene="探索性分析"`；通常 1～4 个步骤；允许少量业务补充；可以参考知识库 |
| 确定性分析 | 用户明确给出步骤、方法、图表或输出格式，或者要求修改已有分析 | `scene="确定性分析"`；完整保留所有步骤；不得改变时间、指标和输出要求；禁止额外发散 |
| 报告解读 | 用户必须明确提到“报告解读”，并且现有报告内容足以回答，不需要补数和加工 | 仅 1 个步骤；`title="报告解读"`；`detail` 为用户问题；`output=""` |
| 无关问题 | 明确与数据分析无关，或者只有“我想分析”这类完全没有目标的表达 | 谨慎拒绝；`detail/output=""`；在 `title` 中礼貌引导用户补充数据需求 |

无关问题采用保守策略：缺少日期、不知道具体处理方式、缺少网络信息，都不能直接判为无关。联网搜索金价、电商热点、战争对油价的影响等泛数据问题，仍然应进入数据分析链路。

DEEP_RESEARCH 模式只有探索性分析、确定性分析、报告解读和无关问题四类意图，普通查数被合并到确定性分析中。

#### 9.3.3 用户需求忠实性约束

| 约束对象 | 必须做到 | 禁止行为 |
| -- | -- | -- |
| 时间 | 保留“昨日、近 7 天、本周、去年同期”等原始表述 | 擅自转换成具体日期，或者改变比较周期 |
| 指标与口径 | 原样保留指标名称、去重维度、统计周期和用户给出的公式 | 根据常识补充公式，或把指标改写成模型理解的另一种口径 |
| 筛选范围 | 完整保留品牌、部门、类目、数据分区和数据粒度 | 丢失筛选条件，或者把用户原词擅自绑定到具体字段 |
| 分析动作 | 用户要求的计算、拆解、排序、对比和展示方式都要写进计划 | 自行增加同比、环比、TopN、概览、探查或总结章节 |
| 输出要求 | 表格、柱状图、字段顺序和固定文案必须写入对应 `output` | 把表格改成图表，或增加用户没有要求的展示方式 |
| 表述完整性 | 直接写明分析对象和条件，每个维度分别保留 | 使用“用户提到的”“这些数据”“按照指示”等模糊代词 |

后续工具看不到 Planner 的 `<think>`，所以时间、口径、筛选条件、数据粒度、公式、分析目标和分析方式都必须显式写进 `make_graph_plan` 参数。Prompt 对此采用的原则是：在不编造的前提下，宁可适当重复，也不能遗漏。

时间处理还有两条专门规则：

- `${day_info}` 只用于帮助理解当前时间，计划中仍保留用户的相对时间表述。
- Prompt 规定 `近N天` 为截至昨天的连续 N 天，例如近 7 天是 `[昨天-6天, 昨天]`；`本周` 是 `[周一, 昨天]`。

#### 9.3.4 步骤粒度和自包含约束

| 规则 | 具体要求 | 解决的问题 |
| -- | -- | -- |
| 原子化对齐 | 数据分析步骤至少包含一次查询、加工或分析，不能只有建议或总结 | 防止产生 Executor 无法真正执行的空步骤 |
| 不过度拆分 | 用户的一步操作保持为一个步骤，例如“计算环比”不能拆成取本期、取上期、计算变化三个步骤 | 避免计划冗长和不必要的跨步骤传递 |
| 筛选与计算合并 | “筛选品牌 A 的 SKU 并计算 GMV”应放在同一个 `detail` 中 | 后一步看不到前一步未输出的中间数据 |
| 禁止空章节 | 不单独设置获取数据、数据概览、数据探查、经营建议、全文总结或综合汇总章节 | 保证每个章节都围绕一个实际分析目标 |
| 步骤自包含 | 每个 `detail` 都要写完整对象、时间、筛选条件和处理动作 | 让每个节点可以脱离 Planner 上下文独立执行 |
| 字段对齐 | 每个 Step 的 `title/detail/output` 含义必须一一对应，`output` 不能省略格式要求 | 防止标题、任务和最终产物错位 |

“每一步必须有数据处理”主要针对查数和分析步骤；报告解读与无关问题是 Prompt 明确规定的特殊场景，本身不要求重新加工数据。

#### 9.3.5 图结构和参数约束

`make_graph_plan` 的核心参数约束如下：

| 参数 | 约束 |
| -- | -- |
| `scene` | 必须属于当前模式允许的意图枚举 |
| `global_config` | 只记录对整个计划都生效的商品范围、时间和筛选条件；没有全局条件或只有一个步骤时可以为空 |
| `steps` | 每个步骤描述一个可执行目标，并包含 ID、标题、详细任务、输出要求和依赖 |
| `layout_config` | 只记录最终报告的展示和排版要求，不允许包含新的数据分析或计算逻辑 |

AUTO 和 REPORT Prompt 对图结构还显式要求：

- Step 数量为 1～10，`id` 是唯一字符串，建议按 `"1"、"2"、"3"` 递增。
- `dependencies` 只能引用已经出现的前置步骤，禁止自依赖和循环依赖。
- 支持串行、共享前置节点后的并行分叉，以及依赖多个前置结果的汇聚。
- 全局条件可以在具体 Step 中重复；当全局条件和步骤内条件冲突时，以步骤内条件为准。

步骤之间不共享未输出的中间上下文，只共享最终结果。因此，某个步骤使用的筛选范围和计算条件必须写在自己的 `detail` 中，不能只写在另一个步骤里。

#### 9.3.6 知识库和 `plan_template` 约束

| 场景 | 约束 |
| -- | -- |
| 默认知识 | Prompt 会提前注入 `${default_knowledge}`，只使用与当前问题相关的内容 |
| 知识不足 | 可以再调用一次 `search_knowledge`；如果用户明确提到知识库内容，则必须使用该工具 |
| 字段知识 | 只能帮助判断某个词属于指标、维度还是筛选条件，不能把用户原词直接改写成“字段=值” |
| 知识收敛 | 高优先级知识已经覆盖问题时必须停止扩展，不能继续联想新的分析逻辑 |
| 模板补充 | `plan_template` 与当前输入没有冲突时取二者的有效并集 |
| 模板时间 | 模板中的绝对时间应被忽略，时间以当前输入为准 |

Prompt 给出的知识优先级是：

```text
plan_template
    > 语义层知识
    > 元数据字段知识
    > 用户知识库
    > 系统知识库
    > 用户提供的数据
```

外部知识的唯一作用是帮助完成用户原始问题，不能借知识库扩大任务范围。尤其是字段知识只能辅助语义理解，例如用户说“家电”，计划中应继续保留“家电”，不能擅自改写成“三级类目=家电”。

#### 9.3.7 `layout_config` 和输出协议约束

REPORT Prompt 对 `layout_config` 做了最完整的限制，只允许保存两类要求：

- 从已经完成的多个分析结果中，只展示用户指定的部分。
- 设置最终报告的特殊标题或排版样式。

相关性、差值、排序、TopN 等需要重新计算的内容必须生成 Step，不能放入 `layout_config`。图表需求也不能设置为查数场景，因为查数链路不负责图表绘制。

Planner 最终只能输出以下协议：

```text
<think>5～10 句简短思考</think>
{
  "tool_name": "make_graph_plan 或 search_knowledge",
  "arguments": {}
}
```

JSON 必须可解析，只能输出上述结构，并尽量少用英文。Few-shot 又进一步约束了典型边界：

| 示例类型 | 示例实际约束 |
| -- | -- |
| 多时间查数 | 保留“昨日、同环比、最近一周日均”的原始时间表述，不转换成日期 |
| SKU 诊断 | 严格保留同比、环比、表格、时间列、柱状图和 Top3 等逐项要求 |
| 多轮追问 | 根据结果规模和可复现性，选择枚举实际值、复述筛选逻辑或引用上一轮结果 |
| GMV 错误示例 | 禁止编造同比、计算方法和图形，同时不能遗漏用户指定的表格 |
| 字段绑定错误示例 | 知识只能辅助理解“秒送组”是筛选概念，不能擅自绑定到部门字段 |
| Layout 错误示例 | 相关性和差值属于新计算，必须放入 Step，不能伪装成排版要求 |

#### 9.3.8 不同模式的约束差异

| 模式 | 意图 | Step Schema | 特殊约束 |
| -- | -- | -- | -- |
| AUTO | 5 类，包含查数 | Prompt 中的 Step 不含 `scene` | 包含完整图规则；图表禁止归为查数 |
| REPORT | 5 类，包含查数 | Prompt 中的 Step 不含 `scene` | 包含完整图规则；重点约束 `layout_config` |
| DEEP_RESEARCH | 4 类，查数并入确定性分析 | Prompt 要求每个 Step 增加 `scene` | 使用追问任务说明，但没有拼接完整 `GRAPH_RULES` 段 |

### 9.4 如何评测

Planner 不适合使用计划文本的精确匹配，因为同一个问题可能存在多种正确规划方式。评测采用两层机制：

1. **硬规则校验**：自动检查 JSON、字段、步骤数量和 DAG 依赖是否合法。
2. **语义评分**：判断意图是否正确、用户要求是否完整、步骤是否合理、依赖是否正确，以及是否擅自增加内容。

| 评分项 | 权重 | 评测内容 |
| -- | --: | -- |
| 意图与模式判断 | 20% | `scene` 是否正确，是否满足不同模式的特殊规则 |
| 需求与约束覆盖 | 30% | 时间、指标、筛选、公式和输出要求是否完整保留 |
| 步骤设计质量 | 25% | 必要任务是否覆盖，粒度是否合理，是否存在冗余步骤 |
| 依赖与可执行性 | 15% | 依赖关系是否符合逻辑，每一步是否能够执行 |
| 忠实性 | 10% | 是否虚构公式、指标、字段或用户未要求的分析 |

同时单独统计以下工程指标：

- JSON 通过率
- DAG 通过率
- 关键要求遗漏率
- 幻觉率
- 一次生成成功率

如果出现 JSON 无法解析、依赖成环或关键业务口径遗漏，应直接判为失败，不能依靠其他评分项补偿。

### 9.5 评测集覆盖范围

- **意图与模式**：五类意图，以及 AUTO、REPORT、DEEP_RESEARCH 三种模式。
- **上下文**：独立问题、多轮追问、条件新增、删除和修改。
- **业务约束**：相对时间、多重筛选、指定公式、指定粒度和指定输出形式。
- **图结构**：单步骤、串行、并行、分叉和汇聚。
- **对抗样本**：知识与用户要求冲突、相似字段误绑定、信息不足、诱导模型补充公式。

线上出现的 Planner Badcase 需要按照 Prompt 版本持续加入固定回归集。

### 9.6 当前模型参数

| 配置 | 模型 | Temperature |
| -- | -- | --: |
| 主模型 | `plan_llm` | `0.1` |
| 备用模型 | `plan_backup_llm` | `0.1` |

Planner 调用模型时只传入 `messages`，没有额外覆盖 temperature。主模型输出为空时会先重试，仍然为空才切换到备用模型。

## 10. Executor Agent 是如何设计、约束和评测的？

当前项目的 Executor 更接近一个代码驱动的 DAG 调度器，而不是让 LLM 自由决定下一步的 ReAct Agent。它接收 Planner 生成的 `GraphPlan`，按照依赖关系调度步骤，把每个步骤交给 `process_and_summary_agent`，再维护状态、附件和执行结果；最终业务报告由后续 `global_summary_agent` 生成。

### 10.1 核心职责与边界

```text
读取 GraphPlan
    ↓
找出依赖已满足的步骤
    ↓
按并发上限启动步骤
    ↓
调用 process_and_summary_agent
    ↓
更新步骤状态、结果和附件
    ↓
继续调度后续步骤
    ↓
输出步骤执行账本
```

| Executor 负责 | Executor 不负责 |
| -- | -- |
| 按依赖关系决定步骤何时启动 | 重新理解用户意图或修改分析目标 |
| 控制串行、并行、分叉和汇聚 | 重新设计 Planner 的步骤内容 |
| 向下游传递当前步骤和依赖结果 | 展开下游专业 Agent 的数据处理逻辑 |
| 记录 `continue/skip`、步骤摘要和附件 | 直接生成最终业务报告 |
| 处理部分失败、全部失败和指定步骤重跑 | 评价最终报告的表达质量 |

在当前主链路中，查数任务会走 `query_data_flow`，单步骤分析会走 `easy_analysis_flow`；`data_executer` 主要负责多步骤复杂计划。

### 10.2 Executor 的输入和状态

Executor 从 `shared_data["plan"]` 读取 `GraphPlan`，核心字段如下：

| 字段 | 作用 |
| -- | -- |
| `id` | 步骤唯一标识，用于建立依赖关系 |
| `title` | 步骤标题 |
| `step_command` | 当前步骤需要执行的完整指令 |
| `dependencies` | 每个步骤依赖的前置步骤 ID |
| `step_result` | 每个步骤的执行摘要 |
| `step_status` | 每个步骤的执行状态 |
| `plan_attachment` | 每个步骤产生的文件、代码或其他附件 |
| `completed_step` | 当前已经完成的步骤数量 |

Executor 收到的 query 是固定执行指令，真正的业务要求主要来自 `GraphPlan.step_command`。系统还会注入数据摘要、历史消息、当前步骤状态以及直接依赖步骤的执行 Memory。

### 10.3 Prompt 涉及哪些内容

当前仓库中的默认 Executor Prompt 很短，没有 Planner 那样的大量意图规则和业务 Few-shot，主要约束执行节奏与工具调用格式。

| 方面 | Prompt 约束 |
| -- | -- |
| 角色 | 定义为京东平台内部的商业数据分析执行专家，只负责执行既有计划 |
| 概念 | 区分整体 `plan` 与单个 `step`，每个步骤围绕一个主题和数据结论 |
| 数据源 | 支持本地 Excel、CSV 文件和在线 ClickHouse 数据集 |
| 工具 | 通过 `${filter_tools_description}` 注入当前可用工具 |
| 数据摘要 | 通过 `${all_data_summary}` 注入可用数据概况 |
| 执行顺序 | 重复执行“获取计划状态 → 调用一次数据加工工具 → 更新计划状态” |
| 调用次数 | 每轮只能调用一次数据加工工具，禁止连续调用多个加工工具 |
| 状态更新 | 数据加工完成后必须调用 `update_plan` |
| 输出格式 | 只输出一次简短 `<think>` 和一个包含 `tool_name/arguments` 的 JSON |

Prompt 可以由 LAF 的 `executor_prompt` 在线覆盖，因此离线评测需要记录实际生效的 Prompt 文本或版本哈希。

### 10.4 Prompt 约束和代码硬约束

| 约束层 | 当前实现 |
| -- | -- |
| 计划状态 | Prompt 要求调用 `get_plan_status`；代码并未注册这个工具，而是直接向上下文注入已完成、当前和未来步骤 |
| 单步加工 | 代码对每个步骤固定调用一次 `process_and_summary_agent(command="start")` |
| 依赖调度 | 只有未完成、未运行且依赖已满足的步骤才能进入候选集合 |
| 串行降级 | 完全没有 `dependencies` 时，默认按步骤顺序串行执行 |
| 并行控制 | 多个无依赖或依赖已满足的步骤可以并行，但不能超过 `max_concurrent` |
| 上下文隔离 | 独立分支不共享结果；子步骤只继承直接依赖步骤的增量 Memory |
| 请求隔离 | 并行步骤使用独立的 request 和 `shared_data` 副本，并写入各自的 `current_step_index` |
| 状态协议 | `update_plan` 要求返回 `command=continue/skip` 和 `step_summary` |
| 状态落盘 | 调度代码负责更新 `step_status`、`step_result`、`completed_step`、附件和共享计划 |

步骤完成后，无论并行完成顺序如何，最终 Memory 和步骤结果都会按原计划索引重新汇总。Executor 返回的是步骤执行账本，正常情况下再由 `global_summary_agent` 基于执行过程生成最终回答。

### 10.5 LLM 在 Executor 中的真实作用

`master_config.use_llm` 决定 Executor 是否使用 LLM 判断步骤状态，本地默认值是 `false`。

| 模式 | 实际行为 |
| -- | -- |
| `use_llm=false` | 代码直接调用一次 `process_and_summary_agent`，随后固定生成 `update_plan(command="continue")`，不让 Executor LLM 判断成功或失败 |
| `use_llm=true` | `plan_llm` 读取步骤执行结果并生成 `update_plan`；如果 JSON 解析失败或工具名不是 `update_plan`，回退为默认 `continue` |
| 全部步骤为 `skip` | 使用主模型生成一句整体失败说明；主模型输出为空时再调用备用模型 |

因此，默认路径下 Executor 的调度、工具调用和状态推进主要由代码决定，Prompt 对主流程的影响较小。真实的数据结果主要保留在步骤 Memory 和附件中，默认 `step_summary` 只是通用的完成说明。

### 10.6 如何评测 Executor

Executor 不适合以最终答案文本相似度作为主要指标，应当直接检查执行 Trace、任务启动时间和 `shared_data["plan"]` 的状态变化。

首先设置以下硬门槛：

- 任何步骤都不能在有效依赖完成前启动。
- 每个待执行步骤只能调用一次下游 Agent，不能遗漏或重复执行。
- 实际并发数不能超过配置上限，合法 DAG 不能死锁。
- 状态、结果和附件必须与步骤索引一一对应。
- 执行结束时，完成数量和终态必须与真实执行情况一致。

| 评分项 | 权重 | 评测内容 |
| -- | --: | -- |
| DAG 调度正确性 | 30% | 就绪节点选择、依赖顺序、串并行和汇聚是否正确 |
| 步骤派发与上下文 | 25% | 当前步骤指令、依赖 Memory 和 `current_step_index` 是否正确 |
| 状态与结果一致性 | 20% | `step_status`、`step_result`、附件和完成数量是否对齐 |
| 失败与重跑 | 15% | `skip/error`、全部失败、指定步骤重跑和缓存复用是否正确 |
| 性能与资源 | 10% | 峰值并发、关键路径耗时、相对串行加速比和冗余调用次数 |

建议单独统计：依赖违规率、步骤遗漏率、重复执行率、状态误判率、LLM 解析回退率、死锁识别率、重跑覆盖率、缓存命中率和 P95 单步耗时。

### 10.7 评测集覆盖范围

| 类型 | 需要覆盖的案例 |
| -- | -- |
| DAG 形态 | 纯串行、多个并行根节点、扇出、扇入、菱形结构和多个独立子图 |
| 完成状态 | 全部成功、部分 `skip`、全部 `skip`、空结果、下游异常和非法 command |
| 上下文传递 | 单依赖、多依赖汇聚、独立分支隔离和附件传递 |
| 并发场景 | 不同步骤随机延迟、乱序完成、并发上限为 1/2/6 |
| 异常计划 | 未知依赖、重复 ID、循环依赖和计划字段长度不一致 |
| 重跑场景 | 从首步、中间步骤和末步重跑，修改步骤指令以及前置缓存复用 |
| 配置差异 | `use_llm=false/true`、不同 Prompt 版本和不同并发上限 |

隔离评测时，可以把 `process_and_summary_agent` 替换为返回固定结果、固定附件和可控延迟的 Fake Agent。这样能够先验证 Executor 调度本身；再固定步骤执行结果、单独打开 `use_llm=true`，评测 `update_plan` 的状态判断和摘要忠实性。

### 10.8 当前模型与运行参数

| 配置 | 当前值 |
| -- | -- |
| 主模型 | `plan_llm`，temperature `0.1` |
| 备用模型 | `plan_backup_llm`，temperature `0.1` |
| `use_llm` | LAF 配置控制，本地默认 `false` |
| 最大并发 | LAF `max_concurrent` 控制，本地默认 `6` |
| Executor 超时 | 24 小时 |
| Executor 重试 | 注册时没有显式设置 |

另外需要留意：当前实现会忽略未知依赖，且 `skip/error` 也会解除下游依赖；默认 `use_llm=false` 时还会直接把正常返回的步骤标记为 `continue`，这些场景应优先加入回归测试。

## 11. `process_and_summary_agent` 是如何设计、约束和评测的？

`process_and_summary_agent` 不是一个依靠独立 Prompt 自由决策的 Agent，而是一个代码驱动的复合工作流。它把 Planner 当前步骤交给 `process_expert` 完成取数、计算和节点结论生成，再把结果交给 `summary_expert` 做汇总、表格修复和可视化，最终返回当前步骤的业务结论。

以下内容基于仓库提交 `4cf2ba6e` 的静态实现，核心代码位置如下：

| 代码位置 | 作用 |
| -- | -- |
| `applications/master_agent/run_master_0130.py:360` | 注册 `process_and_summary_agent`、`process_expert`、`Text取数Agent` 和 `summary_expert` |
| `applications/master_agent/agent/master_graph_flow.py:688` | 定义组合工作流 `combine_data_expert_workflow` |
| `applications/data_process/agents/data_process_workflow.py:99` | 组装数据处理 Prompt、可用工具和返回结构 |
| `applications/data_process/util/llm_response_parser.py:442` | 拦截并处理虚拟的 `summary_tool` |
| `applications/summary_agent/workflow/node_summary_workflow.py:7` | 从当前步骤附件提取 `process_expert.conclusion` |
| `applications/summary_agent/workflow/node_summary_and_visual_workflow.py:8` | 检查图表占位符并按需调用 `visual_agent` |

### 11.1 核心职责与边界

```text
读取当前 GraphPlan 步骤
    ↓
拼接 title + step_command
    ↓
调用 process_expert
    ↓
保存 process_expert 附件
    ↓
调用 summary_expert
    ↓
保存 summary_expert 附件
    ↓
返回当前步骤结论
```

| 负责内容 | 不负责内容 |
| -- | -- |
| 执行 Planner 已确定的当前步骤 | 重新识别用户意图或修改 Planner 计划 |
| 串联数据处理和节点汇总两个阶段 | 调度整个 DAG 或决定下一步何时执行 |
| 保存当前步骤的处理结果和总结附件 | 生成跨步骤的最终完整报告 |
| 返回当前步骤可供 Executor 使用的结论 | 自己维护步骤依赖和全局完成状态 |

因此，它位于 Executor 和数据处理子系统之间：Executor 决定“执行哪个步骤”，`process_and_summary_agent` 负责“把这个步骤执行完并产出节点结果”。

### 11.2 输入、上下文与输出契约

注册时要求输入包含 `command`，接口文案约定值为 `start`。但当前 Schema 只设置了 `required=["command"]`，没有真正声明 `enum`，组合工作流内部也没有读取或判断 `command` 的值。

真正的业务输入来自 `shared_data["plan"]`：

| 输入 | 来源 | 用途 |
| -- | -- | -- |
| `current_step_index` | Executor 写入 `shared_data` | 确定当前执行哪个步骤，缺省值为 `0` |
| `title` | 当前 `GraphPlan` 步骤 | 表明当前步骤主题 |
| `step_command` | 当前 `GraphPlan` 步骤 | 包含完整的数据范围、筛选条件、计算动作和输出要求 |
| 直接依赖结果 | Executor 注入的步骤 Memory | 为当前步骤提供必要的前置结论 |
| 数据集、文件、知识和临时文件信息 | 当前请求上下文 | 供 `process_expert` 选择取数和加工工具 |

组合工作流将当前步骤拼成：

```text
query = current_title + "\n" + current_command
```

最终返回值是 `summary_expert_res.output`，即当前步骤的总结文本；同时会在当前步骤附件中保存：

```text
process_expert: 结构化的数据处理结果列表
summary_expert: 当前步骤最终总结文本
```

### 11.3 整体处理流程与双阶段分工

| 阶段 | 输入 | 主要动作 | 输出 |
| -- | -- | -- | -- |
| `process_expert` | 当前步骤的 `title + step_command`、数据源、历史和依赖上下文 | 取数、代码计算、结果校验，并通过 `summary_tool` 生成节点结论 | 包含 `output_data`、`conclusion`、`process_data_ids` 的列表 |
| 附件交接 | `process_expert` 返回值 | 尝试解析字符串 JSON，并写入当前步骤附件 | `attachment["process_expert"]` |
| `summary_expert` | 当前步骤附件中的 `process_expert` 结果 | 提取并拼接 `conclusion`，修复 Markdown，按需生成图表 | 当前步骤总结文本 |
| 结果写回 | `summary_expert` 输出 | 发送步骤结果消息并保存附件 | `attachment["summary_expert"]` 和工作流返回值 |

这两个阶段不是重复总结：`process_expert` 内部的 `summary_tool` 负责基于真实工具结果形成受约束的业务结论；`summary_expert` 主要负责从附件中汇总已有结论和处理可视化。

### 11.4 `process_expert`：取数、计算与结论生成

`process_expert` 本身也是一个 `WorkflowAgent`，真正使用 LLM 的是内部 `Text取数Agent`。数据处理工作流会根据本地文件、在线数据集、是否属于“查数”场景以及可选工具，动态组装 Prompt 和工具说明。

#### 11.4.1 有效 Prompt 涉及哪些方面

| 方面 | 主要规则 |
| -- | -- |
| 角色与范围 | 定义为数据分析程序员，只执行用户明确要求的取数、计算和分析，不主动增加最大值、平均值、趋势等内容 |
| 执行顺序 | 先取数，再按需加工，最后总结；只有用户明确要求进一步分析时才使用代码加工 |
| 工具选择 | 在线数据优先使用 `text2data_tool`，本地文件和复杂计算使用 `py_coder_tool`，指标分析命中白名单时可优先使用 `metric_analyze_tool` |
| 工具切换 | 同一时刻只能使用一个业务工具，切换前必须调用 `get_tool_documentation`，禁止臆造工具参数 |
| 用户要求 | 时间、指标、筛选条件、计算口径、排序和输出格式都必须完整保留 |
| 数据真实性 | 最终数字必须来自已经执行的工具，禁止在总结阶段自行做加减乘除或编造派生指标 |
| 异常处理 | 空数据属于正常结果，直接如实总结；查询异常根据错误有限重试，避免无限循环 |
| 最终结束 | 所有取数和计算完成后必须切换到 `summary_tool`，不允许直接输出自然语言答案 |

#### 11.4.2 数据处理结果契约

`Text取数Agent` 返回后，`data_process_workflow` 会从 ReAct Memory 中提取实际工具执行详情，并包装为：

```json
[
  {
    "output_data": [
      {
        "data": "工具执行详情"
      }
    ],
    "conclusion": "summary_tool 生成并处理后的结论",
    "process_data_ids": ["当前步骤新产生的临时数据 ID"]
  }
]
```

其中 `conclusion` 已经是经过 `summary_tool` 约束和后处理的文本，后续 `summary_expert` 不会重新执行数据计算。

### 11.5 `summary_tool`：结束协议与校验链

`summary_tool` 不是 `summary_expert` 的工具，也不是一个可以被 `oxy_request.call("summary_tool")` 执行的真实 Tool。它是当前项目基于 Oxygent ReAct 机制实现的虚拟结束协议：通过工具说明约束模型输出，再由自定义解析器拦截该输出并转换成 `ANSWER`。

标准输出协议为：

```json
{
  "tool_name": "summary_tool",
  "arguments": {
    "summary": "基于前序工具结果形成的最终业务结论"
  }
}
```

`summary_tool` 的完整处理链如下：

```text
模型生成单个 summary_tool JSON
    ↓
解析 arguments.summary
    ↓
AI 质量裁判
    ↓
数字溯源校验
    ↓
独立 LLM 数字标签化
    ↓
数据源 ID 修复
    ↓
Markdown 表格修复
    ↓
数字标签渲染
    ↓
返回 LLMState.ANSWER
```

#### 11.5.1 AI 质量裁判

裁判输入包含当前步骤 query、待检查的 summary 以及 `Text取数Agent` 的 `full_memory`。`node_judge_agent` 先生成动态检查规则，再结合静态硬规则调用 `judge_tool`，重点检查用户要求、单位、口径、数据一致性、时间、格式和截断说明。

当前重试策略是：

- 第一次明确判定不通过时返回 `ERROR_PARSE`，把违规规则和修改建议写回 ReAct 上下文。
- 同一次执行后续生成的新 summary 不会再次进入裁判，即裁判最多真正执行一次。
- 裁判调用异常或超时时降级放行，不阻塞主流程。

#### 11.5.2 数字溯源校验

数字溯源会从 summary 中抽取业务数字，再检查这些数字是否能在 `full_memory` 的非 System 消息中找到。日期、章节序号、列表序号、`<datasource>` ID 和 `<jmtCharts>` 占位符中的数字会被排除。

`full_memory` 的组成是：

```text
动态 System Prompt
    + 继承的 short_memory
    + 当前步骤 query
    + 当前 Text取数Agent 的 ReAct 历史
        - 模型发出的工具调用
        - text2data_tool / py_coder_tool 等工具返回结果
```

因此，数字溯源主要依赖当前 `process_expert` 内部 `Text取数Agent` 的上下文，而不是读取已经保存的 `process_expert` 附件。附件是在 `summary_tool` 完成并返回之后才创建的。

需要注意，校验范围并非严格限定为“当前工具结果”：当前 query 和 short memory 也属于非 System 消息，如果某个数字只在用户问题或历史对话中出现，也可能通过校验。数值比较还允许约 `1%` 的相对误差，并接受正负数绝对值匹配。

数字溯源的失败策略是：

- 第一次发现无来源数字时返回 `ERROR_PARSE`，要求重新生成。
- 第二次仍有可疑数字时只记录日志并放行。
- `full_memory` 为空、历史中没有可识别数字或校验过程异常时，也会降级放行。

#### 11.5.3 数字标签化与格式修复

数字溯源通过后，会独立调用 `extract_tag_llm`，将自然语言中的裸数字转换为结构化标签：

```text
{num: 原始数值, format: "origin/unit/decimal_value/percent_value"}
```

标签中的 `num` 保留原始值，后续 `NumberTagProcessor` 再统一处理千分位、万/亿单位、小数位和百分比。例如，模型先原样输出 `12345678`，后置渲染可以将其展示为 `1,234.57万`。

后处理还会：

- 修复数据源 ID 的简写格式。
- 修复 Markdown 表头和分隔行的列数。
- 将连续出现的“万万”替换为“亿”。
- 标签化 LLM 返回为空、内容过短或调用异常时，保留原始 summary。

这里的设计意图是把“数据真实性”和“展示格式化”分开：总结模型不能自行改数字，最终展示由统一后处理完成。

### 11.6 `summary_expert`：汇总、可视化与附件写回

`summary_expert` 没有独立的文字总结 Prompt，文本阶段主要由固定代码完成：

1. 从当前步骤附件读取 `attachment["process_expert"]`。
2. 遍历结果列表并提取每个元素的 `conclusion`。
3. 按顺序拼接所有非空结论。
4. 尝试修复 Markdown 表格。
5. 检查是否存在 `<jmtCharts>` 可视化占位符。
6. 如果存在占位符，则调用 `visual_agent`，并用图表结果替换占位符。

当前替换逻辑只处理第一个 `<jmtCharts>` 占位符，因此多图场景需要单独加入评测，不能只验证“是否调用了 `visual_agent`”。

| `summary_expert` 可以做 | `summary_expert` 不应做 |
| -- | -- |
| 合并当前步骤已有结论 | 重新取数或写代码计算 |
| 修复 Markdown 表格 | 修改指标口径或生成新数字 |
| 将可视化占位符替换为图表 | 从其他步骤附件随意补充结论 |
| 返回适合当前节点展示的文本 | 生成跨步骤的最终全局报告 |

组合工作流调用 `summary_expert` 时传入固定 `query="无"`，说明它真正依赖的是当前步骤附件，而不是新的自然语言指令。

### 11.7 Prompt 约束和代码硬约束

`process_and_summary_agent` 本身没有独立 Prompt，约束来自三层：

| 约束层 | 约束方式 | 强度 |
| -- | -- | -- |
| 组合工作流代码 | 固定执行 `process_expert → 保存附件 → summary_expert → 保存附件 → 返回` | 硬约束 |
| `process_expert` 动态 Prompt | 约束工具选择、执行顺序、需求忠实性、数据真实性和最终使用 `summary_tool` | 软约束 |
| `summary_tool` 解析器 | 检查 JSON、裁判、数字溯源、格式化，并通过 `ANSWER/ERROR_PARSE` 控制 ReAct | 代码校验与降级策略结合 |
| `summary_expert` 固定工作流 | 只读取附件中的 `conclusion`，修复表格并按需可视化 | 硬约束 |

主要运行时约束如下：

| 场景 | 当前行为 |
| -- | -- |
| `process_expert` 调用异常 | 直接返回“当前步骤无法顺利执行，请执行下一步骤”，不再调用 `summary_expert` |
| `process_expert` 返回字符串 | 尝试 `json.loads`；解析失败则保留原值继续保存 |
| 保存 `process_expert` 附件失败 | 只记录日志，仍继续调用 `summary_expert` |
| `summary_expert` 调用异常 | 当前函数没有局部捕获，异常向上抛出，由 `WorkflowAgent` 重试机制处理 |
| 保存 `summary_expert` 附件失败 | 只记录日志，仍返回 summary 文本 |
| 组合 Agent 重试 | `retries=3` |
| 组合 Agent 超时 | 3 小时 |

当前实现还存在以下边界：

- Prompt 要求必须先切换到 `summary_tool`，但解析器没有校验 `current_tool_name`，模型直接返回合法的 `summary_tool` JSON 也能结束。
- `Text取数Agent` 达到最大 20 轮后会直接生成兜底答案，这条路径可以绕过 `summary_tool`。
- 数字标签化后的完整合规校验目前被注释，标签化后不会再次进行数字溯源。
- 单个数值标签解析失败时可能被替换为 `-`，需要在回归测试中检查关键数字是否丢失。
- `process_expert` 的注册描述写着“不能输出结论”，但实际会通过 `summary_tool` 返回 `conclusion`，描述与实现语义不完全一致。
- 同名附件采用追加而不是覆盖，Agent 重试或步骤重跑时可能出现重复的 `process_expert` 或 `summary_expert` 结果。
- 公共 Prompt 要求数字保留两位小数并转换万/亿，而 `summary_tool` 描述要求模型保留原值、不得自行换算；设计意图是交给后处理统一格式化，但 Prompt 文案仍应统一。

### 11.8 如何评测

评测不应只比较最终文本相似度，因为同一份数据可以有多种正确表达。应同时检查真实工具结果、ReAct Trace、附件、节点输出和异常状态。

首先设置以下硬门槛：

- 必须使用当前 `current_step_index` 对应的 `title` 和 `step_command`，不能串步骤。
- 正常路径必须先调用一次 `process_expert`，成功后再调用一次 `summary_expert`。
- `process_expert` 异常时不得继续执行 `summary_expert`。
- `process_expert` 和 `summary_expert` 附件必须保存到正确的步骤索引。
- 最终返回文本必须与 `summary_expert` 输出一致。
- 结论中的关键数字、时间、指标和筛选条件必须与工具结果和当前步骤要求一致。
- 并行步骤之间不能读取或覆盖其他步骤的附件和 ReAct 上下文。

| 评分项 | 权重 | 评测内容 |
| -- | --: | -- |
| 数据处理正确性 | 30% | 工具选择、查询条件、计算结果和异常处理是否正确 |
| 用户要求覆盖 | 20% | 时间、指标、筛选、公式、粒度和输出格式是否完整执行 |
| 节点结论忠实性 | 25% | 数字、单位、表格、数据源和可视化是否忠于真实结果 |
| 工作流交接与隔离 | 15% | 调用顺序、步骤索引、附件写入和并行上下文隔离是否正确 |
| 稳定性与效率 | 10% | 重试、超时、降级、冗余工具调用和单步耗时是否合理 |

建议单独统计以下工程指标：

- 当前步骤指令匹配率
- 工具路由正确率
- 数字原值一致率
- 无依据数字率
- 关键要求遗漏率
- 额外分析发生率
- 附件写入完整率
- 跨步骤上下文污染率
- 失败误判为成功的比例
- `summary_tool` 首次通过率和平均重试次数
- P95 单步骤耗时

### 11.9 评测集覆盖范围

| 维度 | 需要覆盖的案例 |
| -- | -- |
| 数据源 | 仅本地文件、仅在线数据集、本地与在线混合、存在临时加工文件 |
| 任务类型 | 简单查数、过滤、聚合、多指标、排序、同环比、占比、趋势和原因分析 |
| 输出形式 | 单句、列表、Markdown 表格、固定模板、详细分析和可视化占位符 |
| 依赖上下文 | 无依赖、单依赖、多依赖汇聚，以及与当前步骤无关的历史干扰 |
| 数据状态 | 正常、空数据、缺失值、异常值、结果截断和超大表格 |
| 格式异常 | 多个 JSON、缺少 `summary`、非法 JSON、错误数据源 ID 和损坏的 Markdown 表格 |
| 工具异常 | 取数异常、代码执行异常、超时、空输出和工具返回结构变化 |
| 工作流异常 | `process_expert` 异常、附件保存失败、`summary_expert` 异常和可视化失败 |
| 数字对抗 | 编造数字、舍入数字、单位换算、同值错指标、历史数字污染和标签化后改数 |
| 并发隔离 | 多个步骤随机延迟、乱序完成、相同指标不同筛选条件和附件索引冲突 |

评测建议分三层进行：

1. **组合工作流单测**：用 Fake `process_expert` 和 Fake `summary_expert` 返回固定结果、异常和延迟，只验证调用顺序、早停、附件和最终返回。
2. **阶段隔离评测**：固定 `process_expert` 输出，单独评测 `summary_tool` 的校验链和 `summary_expert` 的拼接、表格修复及可视化。
3. **冻结数据端到端评测**：使用固定 CSV、固定在线查询快照和黄金计算结果，验证从步骤指令到节点结论的完整正确性。

线上 Badcase 应按 Prompt 版本、模型版本和工具版本进入固定回归集，尤其关注数字错配、额外分析、空数据误写为 0、截断未说明和跨步骤附件污染。

当前静态扫描没有发现这条链路对应的有效自动化测试，因此上述三层评测需要优先补齐，并将附件重复、多图占位符和最大轮次兜底纳入首批回归集。

### 11.10 当前模型与运行参数

| 组件 | 模型或参数 | 实际作用 |
| -- | -- | -- |
| `process_and_summary_agent` | `workflow_llm`，temperature `0.01` | WorkflowAgent 必填占位模型，组合工作流本身不直接调用 |
| `process_expert` | `workflow_llm`，temperature `0.01` | WorkflowAgent 占位，实际文本生成由内部 Agent 完成 |
| `Text取数Agent` 主模型 | `text2data_llm`，temperature `0.1` | 负责取数、工具调用以及生成 `summary_tool` JSON |
| `Text取数Agent` 备用模型 | `text2data_llm_backup`，temperature `0.1` | 主模型异常时备用 |
| 数字标签模型 | `extract_tag_llm`，temperature `0.0` | 将 summary 中的裸数字转换成结构化数值标签 |
| `Text取数Agent` 最大轮次 | `20` | 达到上限后进入直接生成答案的兜底路径 |
| `process_and_summary_agent` | 重试 `3` 次，超时 `3` 小时 | 控制组合工作流整体重试和执行上限 |

面试时可以这样回答：

> `process_and_summary_agent` 是一个确定性的复合工作流，而不是拥有独立 Prompt 的自由决策 Agent。它先把 Planner 当前步骤交给 `process_expert`，由内部 ReAct Agent 完成取数、计算，并通过虚拟的 `summary_tool` 在最终输出前统一执行质量裁判、数字溯源和格式化；随后将结构化结果写入附件，再由 `summary_expert` 提取已有 `conclusion`、修复表格并按需生成可视化。评测时我会拆成数据处理正确性、节点结论忠实性、工作流交接与并发隔离、异常恢复四部分，并通过 Fake Agent 单测、阶段隔离评测和冻结数据端到端评测逐层定位问题。
