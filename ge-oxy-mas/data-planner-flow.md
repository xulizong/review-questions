# Data Planner 多轮 Query Rewrite 面试回答

> 表述原则：重点讲清楚项目中的技术设计和自己真正参与的部分。当前项目已经存在显式多轮 Query Rewrite，但它位于 `/data/query_router`；主 `/chat` 链路目前采用 Planner 结合历史生成完整计划的“隐式意图补全”，两者尚未直接串联。

## 60 秒回答

这个项目的数据问答场景存在大量多轮追问，例如用户第一轮问“查询华北销售额”，第二轮只说“那华东呢”。如果直接把“那华东呢”交给知识召回、路由和取数模块，下游无法确定指标和分析动作。

因此项目中设计了一层面向数据分析场景的 Query Rewrite：根据 `from_trace_id` 找到最近几轮历史，让模型先判断当前问题是否可以独立理解。如果是完整的新问题，就保持原文；如果是省略、指代或下钻类追问，就从最近的历史用户问题中继承必要的主体、指标、时间和维度，生成一个可以独立执行的 `rewritten_query`。例如把“那华东呢”改写为“查询华东地区的销售额”。

重写时我会保留 `original_query`、`rewritten_query` 和 `reason`：重写后的问题用于路由、知识召回和 Planner，原始问题用于前端展示、日志审计和问题回溯。整个过程采用 fail-open 策略，历史查询、模型调用或 JSON 解析失败时继续使用原问题，不能让重写模块阻断主流程。

在 Data Planner 层还会继续结合两类上下文：Planner 历史用于理解上一轮是怎么规划的，Master 历史用于了解上一轮最终执行出了什么结果。最终 Planner 生成包含完整实体、指标、过滤条件和步骤依赖的 graph plan，这相当于在意图层进行第二次规范化。

## 一句话定义

Query Rewrite 不是简单的句子润色，而是把“依赖上下文的当前追问”转换成“语义完整、约束明确、可以被下游独立消费的标准查询”。

## 整体流程

```text
当前 query + from_trace_id
        ↓
加载最近历史问题与回答
        ↓
判断是否需要重写
        ↓
补全主体 / 指标 / 时间 / 维度 / 分析动作
        ↓
original_query + rewritten_query + reason
        ↓
路由 / 知识召回 / Data Planner
        ↓
结合 Planner 历史与 Master 最终结果
        ↓
生成完整 graph plan
```

## 单轮和多轮如何处理

### 单轮完整问题

```text
当前问题：查询 2026 年华东地区销售额
结果：need_rewrite=false
rewritten_query：保持原文
```

单轮对话不会为了“看起来更规范”而强制改写，避免模型改变用户原始意图。

### 多轮省略问题

```text
历史问题：查询华北地区销售额
当前问题：那华东呢？
结果：need_rewrite=true
rewritten_query：查询华东地区销售额
```

这里继承了“查询”动作和“销售额”指标，但以当前问题明确提出的“华东”覆盖历史中的“华北”。

### 结果依赖型追问

```text
历史问题：查询华北地区销售额
历史结果：华北销售额为 120 万
当前问题：和华东相比怎么样？
rewritten_query：对比华北地区与华东地区的销售额
```

这类问题不仅需要历史问题，还可能需要上一轮最终结果。因此 Planner 除了使用自己的计划历史，还需要 Master 保存的最终回答。

## 为什么不直接把全部历史拼给模型

1. 路由、Embedding 检索和知识召回通常只接收一个 query，无法直接消费完整对话消息。
2. 全量历史容易引入无关主题和过期条件，导致模型把已经失效的限制继续带入当前问题。
3. 显式生成 `rewritten_query` 更容易记录、评估和排查，可以明确知道系统最终按什么需求执行。
4. 重写和规划职责不同：重写负责恢复当前问题的完整语义，Planner 负责决定意图类型和执行步骤。

## 历史信息的继承规则

建议采用以下优先级：

```text
当前问题中的显式条件
    > 最近一轮历史用户问题
    > 更早的历史用户问题
    > 历史回答
```

- 当前问题明确说出的实体或指标不能被历史覆盖。
- 优先只使用最近一轮；只有最近一轮无法补全时才向前查找。
- 历史回答主要用于理解“刚才的结果”“与上次相比”等结果型追问，不应优先用于补全实体和指标。
- 不允许引入当前问题和历史中都不存在的信息。

## 结构化输出

```json
{
  "need_rewrite": true,
  "rewritten_query": "查询华东地区的销售额",
  "reason": "当前问题是省略式追问，需要继承上一轮的查询动作和销售额指标"
}
```

结构化输出便于做格式校验、日志记录、失败降级和离线评估。

## 与 Data Planner 的关系

Query Rewrite 和 Data Planner 解决的是两个不同层次的问题：

| 模块 | 解决的问题 | 典型输出 |
|---|---|---|
| Query Rewrite | 用户这句话完整表达是什么 | `查询华东地区销售额` |
| Data Planner | 这个需求属于什么意图、应该怎么执行 | `scene + global_config + graph steps` |

Planner 使用两类历史：

- `master_agent__data_planner`：保存历史 Planner 输入和 graph plan，回答“上一轮系统是怎么理解和规划的”。
- `data_agent__master_agent`：保存用户问题和 Master 最终回答，回答“上一轮最终执行出了什么结果”。

两者结合后可以支持不同追问：

- “那华东呢”主要依赖历史问题和历史计划。
- “和刚才相比呢”需要上一轮最终结果。
- “把刚才结果做成图”需要知道上一轮实际输出，而不只是计划。

## 当前项目中的实际落点

### 已存在的显式重写

- 接口：`/data/query_router`
- 入口：`applications/query_routing/api_handler.py`
- 核心实现：`applications/query_routing/rewrite.py::prepare_query_rewrite`
- 历史：独立的 `query_router_history_prod`
- 默认只读取最近 3 轮历史。
- 只有存在 `from_trace_id` 和历史记录时才调用重写模型；否则保留原问题。

### `/chat` 主链路当前行为

- `pre_process_master_agent` 只做格式解析、占位符替换和 `content` 提取，不做语义重写。
- Master 将历史作为 `user_level_short_memory` 传给 Data Planner。
- Data Planner 通过“系统提示词 + 历史 + 当前 query”生成完整 graph plan，属于 Planner 层的隐式意图补全。
- 当前 `/chat` 不会自动调用 `/data/query_router` 的显式重写结果。

## 推荐的融合方案

不要让 `/chat` 再通过 HTTP 调用 `/data/query_router`，而是将 `prepare_query_rewrite` 抽成可复用的领域服务，并允许调用方传入自己的历史记录。

推荐在 `super_master_workflow` 开始处、知识召回和 Planner 之前执行：

```text
Master 加载 short_memory
        ↓
rewrite(original_query, short_memory)
        ↓
shared_data.original_query = original_query
shared_data.rewritten_query = rewritten_query
shared_data.query_for_search = rewritten_query
        ↓
知识召回 + Planner
```

这样既能让前置召回拿到完整问题，又能继续保留 Master 历史，支持依赖上一轮结果的复杂追问。

## 稳定性设计

- **Fail-open**：重写失败时返回原 query，主流程继续运行。
- **历史窗口**：优先最近 1～3 轮，避免上下文无限增长。
- **双字段保留**：原始 query 用于审计，重写 query 用于执行。
- **结构校验**：只接受合法 JSON，并校验 `need_rewrite` 和 `rewritten_query`。
- **防止幻觉**：Prompt 明确限制只能继承历史中已经出现的信息。
- **可观测性**：记录是否重写、重写原因、耗时和原文/改写文本的哈希，避免日志泄露完整业务数据。

## 面试官常见追问

### 1. 为什么不用 Planner 直接结合历史，非要多一层 Rewrite？

Planner 可以理解历史，但知识召回、Embedding 路由等前置模块在 Planner 之前就需要一个完整 query。显式重写还能提供统一、可审计的下游输入，减少不同模块各自理解历史造成的不一致。

### 2. 如何判断当前问题是不是新问题？

重点判断当前问题是否已经包含完整主体、指标、时间、维度和动作。完整问题或与历史主题明显无关时不改写；省略句、指代句、下钻和对比追问才结合历史补全。

### 3. 如果历史和当前问题冲突怎么办？

始终以当前问题的显式条件为最高优先级。例如历史是“华北销售额”，当前明确说“华东”，只能继承“销售额”和查询动作，不能继续保留“华北”。

### 4. 如何避免把错误历史带进来？

限制历史窗口、优先最近一轮、先判断新问题还是追问，并要求模型输出重写原因。还可以增加实体差异检测：当前主体与历史主体明显无关时直接判定为新问题。

### 5. 如何评估重写效果？

不能只看文本相似度，应该关注：

- `need_rewrite` 判断的准确率和召回率。
- 主体、指标、时间、维度等约束的保留准确率。
- 重写后路由准确率和 Planner 计划正确率是否提升。
- 不需要重写时保持原文的比例。
- P95 延迟、失败降级率和 JSON 解析成功率。

不要在没有真实测试数据的情况下编造提升百分比；可以说明会如何构建多轮追问测试集和评价指标。

### 6. 为什么 Planner 还要使用 Master 历史？

Planner 自身历史只有“历史问题和历史计划”，没有计划执行后的最终业务结果。Master 历史提供上一轮最终回答，用于处理“和刚才相比”“解释刚才的下降”“把刚才结果做成图”等依赖执行结果的追问。

### 7. 这是不是会增加一次模型调用和延迟？

会，因此只在存在历史且当前问题可能依赖上下文时触发；同时限制历史轮数、使用轻量模型，并通过 fail-open 保证重写服务异常时不影响主流程。也可以对历史链和当前 query 的组合结果做短期缓存。

## 个人贡献的诚实表述

根据实际参与范围选择表述，不要把“理解过代码”说成“独立实现并上线”：

- 如果主要做了链路分析和方案设计：`我负责梳理多轮意图补全链路，识别出显式 Rewrite 与 Planner 历史融合割裂的问题，并设计了统一的前置重写方案、上下文优先级和失败降级策略。`
- 如果参与了联调或验证：`我参与了多轮 Query Rewrite 的联调和案例验证，重点覆盖省略、指代、下钻、对比以及新话题切换。`
- 只有确实完成代码落地时再说：`我将 Rewrite 抽成通用服务并接入 Master 前置链路，同时补充了结构校验、降级和多轮测试。`

面试中的技术亮点不在于说“我调用了一个大模型”，而在于能讲清楚为什么重写、历史如何选择、冲突如何解决、失败如何降级，以及如何验证它确实改善了下游路由和计划质量。
