# Text2SQL Agent 简历表达与面试问答

本文用于把当前 Text2SQL Agent 项目转换成简历表述和面试回答口径。内容基于现有代码和项目文档整理，重点突出真实参与价值、架构复杂度、工程约束和可解释的技术结果；未在代码或数据中确认的量化收益使用占位符，不建议直接编造。

## 2. 一分钟项目介绍

这个项目是一个面向业务查数场景的自然语言查询 Agent。用户输入类似“上月各事业部采购亏损金额分布及同比变化情况”，系统先召回报表关联的数据集 schema、字段枚举和业务知识，再判断数据集类型。如果是普通 SQL 数据集，就进入 SQL 生成、执行、纠错和多路径选举；如果是 DSL 数据集，就进入 ReAct 风格的 DSL 查询工具链。最终系统返回结构化查询结果，并在交互式场景里继续生成 SQL 卡片、图表协议和结果总结。

我的工作重点可以概括为三层：第一层是 Agent 编排，把 master agent、场景入口 agent、SQL/DSL 子 agent 和工具链串起来；第二层是 SQL 质量闭环，使用 prompt 约束、解析校验、真实执行、失败纠错和多候选选举保证结果尽量可用；第三层是工程化落地，包括动态 LAF 配置、远程 JSF 服务调用、日志截断、trace 上下文、异常兜底和返回结构统一。

## 3. 面试高频问题与回答

### 1. 这个项目解决了什么问题？

它解决的是业务人员自然语言查数的问题。传统方式需要用户知道数据集字段、SQL 写法和指标口径，而这个 Agent 会把 query、历史上下文、数据集 schema、字段枚举和业务知识组合起来，自动生成 SQL 或 DSL，执行后返回数据、图表和总结。项目难点不只是“让模型写 SQL”，而是要让 SQL 可执行、口径尽量准确、失败能纠错、结果能被前端和用户理解。

### 2. Text2SQL Agent 的整体链路是什么？

请求先进入 master `text_2_sql_agent`，它根据 `shared_data.app/scene/type` 路由到不同 portal agent，例如结构化 API 查询走 `ge_c_query_analysis_agent`，交互式查询走 `ge_c_query_agent`。入口 agent 会转换请求、校验参数、调用 `call_back_dataset_knowledge()` 召回数据集知识，然后用 `dataset_info_tool` 判断是 SQL 数据集还是 DSL 数据集。SQL 数据集进入 `SqlPathRunner` 或多路 SQL 选举；DSL 数据集进入 `dsl_agent` 或多路 DSL 选举。最后统一构造 `Text2SQLResponse`，交互式场景还会继续做 SQL 卡片、图表和 summary。

### 3. `call_back_dataset_knowledge()` 具体做什么？

它负责把用户 query 和数据集 id 转成模型可用的数据集知识。若请求里没有 `dataset_ids`，它会先根据 `bookId` 查询数据集列表；然后调用 `call_back_dataset_full_tool`，最终请求远程 `dataset_rag_rpc_service.callBackDatasetFull`。返回结果会被解析成 `DatasetKnowledge`，里面包括数据集名、字段名、字段类型、字段枚举、`isAgg` 聚合属性、业务知识等。后续 SQL/DSL prompt 依赖这些信息来限制字段选择和指标口径。

### 4. 为什么要区分 SQL 和 DSL 两条路径？

项目里的 SQL 路径面向可以由标准 SQL 查询的数据集，核心是让模型生成 SQL，再交给 `executeSqlAntlr4` 执行。DSL 路径面向 EasyBI/特定语义数据集，模型不能直接随意写 SQL，而是要通过 DSL 工具查询数据，并在必要时用 pandas 做二次加工。两条路径最终都被包装成 `PathState`，所以后续图表、总结和响应构造可以复用。

### 5. SQL 生成是完全靠 prompt 吗？

不是。Prompt 负责告诉模型 SQL 规则，比如只能使用 schema 里的字段、日期如何推导、聚合属性字段必须用 `AGG()`、禁止 `SELECT *`、必要时调用 `convert_calendar`。但代码还有解析和校验：模型输出必须是协议化 JSON，SQL 必须包含 `from` 和数据集表名，`isAgg=1` 字段还会被检查是否按聚合方式使用。不满足时会触发一次提示重试。因此这是 prompt 约束和代码校验共同作用。

### 6. `AGG()` 是什么，为什么不能直接 `SUM()`？

`AGG()` 是平台对聚合属性指标字段的统一聚合入口。对于均价、转化率、百分比、复杂派生指标等非可加性指标，直接 `SUM()` 或二次聚合可能会算错。系统通过 schema 里的 `isAgg` 标记识别这类字段，prompt 要求模型用 `AGG(指标字段)`，代码也会用 SQL 解析工具检查聚合属性字段是否被正确包裹。

### 7. LLM 生成 SQL 后会自己执行验证吗？

LLM 不会自己执行 SQL。生成结果会被 `query_dataset_data_tool` 送到远程 SQL 执行服务，当前主链路使用 `executeSqlAntlr4`。执行结果的 header code 决定这一路是否成功。如果执行失败，系统会根据错误类型判断是否需要纠错；如果成功，结果会进入后续选举或响应构造。

### 8. SQL 失败后如何纠错？

失败后先调用 `is_sql_correction_needed()` 判断是否值得纠错。成功结果不纠错，超时和内存类错误通常也不交给 LLM 修，因为这类问题往往不是简单改 SQL 能解决。其余 DB 错误会先尝试工程规则纠偏，比如 `MissingQuoteSQLCorrection` 处理单引号和反引号混用；仍失败时调用 `llm_dataset_sql_correction_agent`，把 bad SQL 和 DB 错误信息传给纠错 prompt，再执行修正后的 SQL。当前外层 `StatefulRetryExecutor(0, 0)` 不配置多次重试，所以不会无限纠错。

### 9. 为什么要做多路 SQL 选举？

因为复杂自然语言查询可能存在多个合理 SQL 写法，单次模型生成容易受字段选择、日期推导、聚合口径或别名写法影响。多路并发让多个路径各自生成、执行和必要时纠错，最后在成功候选中选出最可信的一条。它不是重复执行同一条 SQL，而是给模型输出增加候选空间，并通过执行结果和规则过滤降低偶发错误影响。

### 10. SQL 多路选举怎么选？

默认策略链先过滤 `is_success=True` 的路径，如果没有成功路径就返回第一条失败路径作为兜底。成功路径多于一条时，再检查聚合属性字段是否按 `AGG()` 规则使用；仍然无法唯一选择时，调用 `llm_dataset_sql_election_agent`，把候选 SQL 和最多前 5 行执行样例拼进 prompt，让模型输出 `<id>`。如果 LLM 选举失败或没有选出合法 id，再用“有数据优先”的工程规则兜底。

### 11. 选举 LLM 会看到全量数据吗？

不会。选举前会复制 `PathState`，成功路径只保留最多前 5 行数据，同时记录总行数 `extra.data_size`。LLM 看到的是用户问题、schema、业务知识、候选 SQL、前 5 行样例和总行数。最终业务返回会映射回原始完整 `PathState`，不会使用裁剪后的结果。

### 12. DSL 多路选举和 SQL 多路选举有什么区别？

DSL 选举的候选内容是 DSL 路径整理出的查询语句、执行结果样例和可能的 pandas 处理信息。它的 prompt 更强调字段语义、DSL 层聚合、日期是否应进入 dimensions、where 中不能出现度量字段、order_by 和 limit 是否符合规则。SQL 选举更关注 SQL 本身和 `AGG()` 规则；DSL 选举更关注 DSL 构建规范和工具调用结果是否回答了用户问题。

### 13. 如何降低模型幻觉？

第一，prompt 只允许使用明确声明的表名和字段名。第二，模型输入来自 `callBackDatasetFull` 返回的 schema、枚举和业务知识，而不是让模型凭空猜字段。第三，输出必须符合 JSON 或 tag 协议，解析失败会进入错误处理。第四，SQL 要真实执行，不能执行就不能作为成功路径返回。第五，对于聚合属性字段，代码会额外做 AGG 校验。多层约束比单纯依赖 prompt 更稳定。

### 14. 日期和农历怎么处理？

SQL 生成 prompt 里有默认日期推导规则，例如近 N 天、本周、本月的计算方式；如果用户明确提到农历日期，`llm_dataset_sql_agent` 和纠错 agent 可以调用 `convert_calendar` 工具做公历/农历转换。DSL prompt 也会注入当前公历日期和农历日期，方便模型在语义层处理相关场景。

### 15. 为什么不把所有逻辑都做成一个大 prompt？

拆成多个 agent 的好处是职责更清楚，也更容易调试。SQL 生成只负责生成候选 SQL，纠错只负责根据 bad SQL 和 DB 错误修复，多路选举只负责比较候选方案，澄清 agent 只负责判断信息是否缺失，summary agent 只负责结果解释。这样每一步都有独立输入、输出和日志，问题定位比一个大 prompt 更容易。

### 16. 这个项目最大的工程难点是什么？

难点在于要把不稳定的 LLM 输出放进可控的数据查询链路。SQL 一旦字段、日期、聚合口径或语法错了，就会影响用户对数据的判断。所以项目不能只追求“生成看起来像 SQL”，而要有 schema 召回、协议解析、执行校验、纠错、选举、日志截断和 trace 追踪。另一个难点是 SQL 和 DSL 两种数据源路径差异很大，但最终还要统一成相同的响应结构。

### 17. 当前方案有什么不足？

多路 SQL 当前输入基本一致，如果多个路径使用相同模型、相同温度和相同 prompt，生成结果可能高度相似，会带来 token 和执行成本浪费。当前质量评估也主要依赖执行成功、规则校验和候选相对选择，不能完全证明业务语义正确。此外，选举 LLM 只看前 5 行样例，适合控制 token，但对某些需要全量分布判断的问题仍有限制。

### 18. 如果继续优化，你会怎么做？

第一，可以增加复杂度判断，简单查询走单路，复杂查询才走多路。第二，可以对生成 SQL 做 normalize 去重，完全相同的 SQL 不重复执行。第三，可以让多路真正差异化，例如不同 prompt 侧重点、不同模型或不同温度。第四，可以沉淀离线评测集，按字段选择、日期范围、聚合口径、执行成功率和结果正确性分维度评估。第五，可以把失败 case 反哺到 prompt 和规则校验里。

## 4. 简历表述中的风险点

不要写“完全解决 SQL 幻觉”或“保证 SQL 语义正确”，因为当前系统仍然依赖 schema 质量、业务知识和模型判断。更稳妥的说法是“构建多层约束和执行校验机制，降低字段幻觉和不可执行 SQL 的影响”。

不要写没有证据的量化指标。除非你能拿到线上数据，否则不要写“成功率提升 50%”或“耗时降低 80%”。可以写“支持执行失败后的自动纠错”“支持 SQL/DSL 多候选选举”“支持结果样例级评估和有界重试”，这些都能从代码解释清楚。

不要把 DSL 路径说成普通 SQL 生成。DSL 路径核心是 ReAct 工具调用和文件结果回读，不是简单让模型直接输出 SQL。面试官如果追问 SQL 和 DSL 的区别，需要明确说明二者执行方式、约束来源和返回包装方式不同。

## 5. 可准备的补充材料

面试前建议准备一个具体例子，例如“上月各事业部采购亏损金额分布及同比变化情况”。用这个例子讲清楚：先召回数据集 schema 和业务知识，再根据 `isAgg` 判断 `采购亏损金额` 必须使用 `AGG()`，然后生成本期和同期 CTE，执行失败时纠错，多路候选成功后按 AGG 规则和结果样例选举。这个例子能同时覆盖 prompt、AGG、执行校验、纠错和选举，是最适合讲深度的案例。

还可以准备一张链路图，按“请求入口 -> 数据集知识召回 -> SQL/DSL 判断 -> SQL/DSL 生成 -> 执行 -> 纠错 -> 选举 -> 图表/总结 -> 响应”的顺序讲。面试官如果关注工程能力，就展开工具调用、异常处理和 trace；如果关注 LLM 应用，就展开 prompt 拆分、协议解析和质量评估。
